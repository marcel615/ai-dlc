# 사용자 주도 공통 계약 관리

공통 루트의 `AGENTS.md`, `docs/workflows/orchestrator.md`, 선택된 `docs/providers/jira.md` 또는 `docs/providers/github-projects.md`와 `docs/review/orchestrator.md`를 읽는다. 필요한 공식 원본이 없거나 확인되지 않으면 추측하거나 대체하지 않고 해당 범위를 보류한다.

`jira` provider는 작업 조회·등록·관련 관계에 `docs/providers/jira.md`를 적용한다. 아래 명세 저장소 Issue 및 Project 등록·GitHub Sub-issue 관계에 관한 지시는 `github_projects`에만 적용한다. 원본 조회·사용자 승인·명세 PR 절차는 공통이다.

사용자가 자연어 또는 명시적 Skill 호출로 직접 요청한 경우에만 실행한다. 다른 Skill의 제안·연결이나 Issue 존재만으로 자동 실행하지 않는다. 공통 루트 `AGENTS.md`, `docs/workflows/orchestrator.md`, `docs/review/orchestrator.md`, 대상 로컬 지시를 따른다. 자연어 변경 요청 또는 지정된 기존 Issue에서 시작하며 선행 Skill 실행은 필요하지 않다. 사용자가 분석만 요청하거나 범위를 제한하면 그 범위를 따른다.

## 원본·Issue와 영향 확인

요청의 목적·변경 범위와 관련 작업·공식 관계·기존 결정을 확인하고, `requirements`와 관련 `contracts`의 설정된 역할·기본 브랜치 원본을 실제 조회해 URL·commit SHA를 기록한다. 기존 구현은 소비자 영향 근거이며 공식 원본 대체가 아니다. 작업 조회·등록은 선택 provider에 따라 구분한다.

- `jira`: 설정된 Jira 프로젝트의 기존 계약 변경 Task를 먼저 조회해 같은 변경을 다루는 작업을 재사용한다. 해당 작업이 없음을 확인한 경우에만 `jira.issue_types.contract`로 생성하고 관련 작업과 연결한다. GitHub Issue 생성과 GitHub Project 등록은 수행하지 않는다.
- `github_projects`: 명세 저장소 및 Project의 관련 열린·닫힌 Issue와 PR을 조회하고 workflow의 계약 변경 Issue 절차에 따라 기존 Issue를 재사용하거나 생성하고 Project에 등록·확인한다.

완료·종료된 과거 작업은 내용과 현재 반영 여부를 확인해 중복 여부를 판단하며 무조건 재사용하거나 재생성하지 않는다. 조회 실패를 작업 부재로 취급하지 않는다. 두 provider 모두 영향 확인에 필요한 GitHub 구현·Issue·PR 조회와 승인된 Specs 명세 PR 생성을 유지한다.

계약 작업을 확인하고 협의·영향 분석을 시작하면 [계약 작업 상태 절차](../../../docs/workflows/orchestrator.md#계약-작업-상태와-머지-후-마무리)에 따라 진행 중으로 전환한다.

요구사항·API·인증·ERD·UI 간 일관성과 필요한 Backend·Frontend 소비자별 영향을 분석한다. 호환성, 기존 데이터·마이그레이션, 보안, 오류·경계 조건, 배포 순서·전환 기간·복구를 관련 범위에서 검토한다. 영향 없음에는 근거를 남기고 미연결·조회 실패는 보류로 구분한다. 관련 작업과 계약 변경 작업을 상호 참조로 연결하되 선택 provider의 기존 관계를 유지한다. `github_projects`에서는 계약 Issue를 임의로 공식 Sub-issue로 추가하거나 URL을 공식 관계로 주장하지 않는다. 각 관련 작업에 영향·이유·재상세화 필요/불필요/판정 보류와 기준 SHA를 기록한다. 사용자 요청 범위 밖 수정은 하지 않는다.

계약 변경 방향과 구현 영향이 충분히 명확해지면 명세 PR 전에 필요한 구현 작업을 준비한다. 기존 열린 작업의 목적·범위를 확인해 맞는 작업을 재사용하고, 꼭 필요하지만 빠진 작업만 선택 provider에 생성·연결한다. 변경안·사용자 결정과 아직 공식이 아닌 상태, 영향·선행 조건·기존 공식 기준 SHA를 구분해 기록한다. 생성은 명세 수정 승인이나 개발 착수가 아니다. 실제 Merge 후 공식 SHA를 확인해 영향 작업의 기준과 재상세화 필요성을 갱신한다. 대상·중복·필요성·관계가 불명확하면 해당 범위를 보류한다.

`jira`의 신규 구현 Task에는 `docs/providers/jira.md`의 구현 유형·역할 라벨·초기 백로그 상태·중복 확인 규칙을 적용한다. `jira.issue_types.implementation`으로 생성하고 Backend에는 `jira.role_labels.backend`, Frontend에는 `jira.role_labels.frontend`를 붙이며 `jira.statuses.backlog`에 둔 뒤 실제 결과를 확인한다. 기존 Task를 재사용할 때는 진행 상태를 되돌리지 않고 `jira.statuses.ready` 전환은 사용자에게 남긴다. 이 규칙은 후보 승인 절차나 `backlog-refinement` 실행을 요구하지 않는다.

## 협의·승인과 명세 PR

결정이 필요한 항목을 의존성과 사용자의 부담을 고려해 하나 또는 관련된 소수의 질문으로 나눈다. 각 항목의 현재 기준·결정이 필요한 이유, 실현 가능한 선택지·장단점, 권장안과 이유를 대화로 제시하고 사용자의 답을 기다린다. 답이 다른 선택에 미치는 영향을 설명하며 필요한 후속 항목을 이어서 협의한다. 이미 확인한 결정을 반복 질문하지 않고, 권장안·예시·침묵을 사용자 결정으로 취급하지 않는다.

협의 중에도 확인된 선택과 출처·범위, 제안·대안·이유, 남은 질문을 구분해 기록하고 재조회한다. `jira`에서는 협의 내용을 댓글로 작성하지 않고, 연결된 Confluence 페이지에 간결하게 기록하며 계약 작업과 영향받는 작업의 본문에는 필요한 상태·영향·링크를 반영한다. Confluence 기록과 Jira의 본문·관계 처리 및 부분 실패는 `docs/providers/jira.md`를 따른다. 기존 기록과 사용자 변경을 보존하고 접근·쓰기 실패는 구분해 보고한다. 공통적으로 적용할 가치가 있는 설계 원칙은 짧은 결정 기록 초안을 제안하되 사용자의 판단과 제안을 혼동하지 않는다.

개별 항목의 선택과 전체 명세 수정 승인을 구분한다. 협의된 변경 범위와 미결 조건을 검토 가능하게 정리하고, 의도된 계약 변경에 대한 사용자의 명시적 승인을 받은 뒤에만 관련 공식 명세를 수정한다. 승인되지 않은 변경은 확정 반영하지 않는다. 수정 전 실제 기본 브랜치의 최신 SHA와 승인·관련 Issue를 다시 확인하고, 기준이 바뀌어 승인 범위나 영향이 달라지면 재협의한다.

대상 Git 루트·원격·로컬 지시·작업 트리와 대상 PR 템플릿을 확인하고 기존 작업을 보존한다. 승인된 공식 원본만 작업 브랜치에서 수정하고 설정된 검증이 있으면 실행한다. 테스트 설정이 없거나 불명확하면 추측하지 않고 미검증을 보고한다. 공식 원본이 다른 저장소나 작업 트리에 있어 경로·원격·권한이 불명확하면 해당 부분을 보류한다. `orchestrator.default_branch`에 직접 Push하지 않는다. 변경 Issue와 승인 근거, 기준 SHA, 소비자 영향·미결 조건·검증 결과를 담은 PR을 대상 원본 저장소의 기본 브랜치로 생성한다. 권한이나 도구 제한으로 PR을 만들지 못하면 실제 완료 단계와 재개 조건을 보고한다. 사용자가 직접 Merge하며 자동 Merge하지 않는다.

검토 가능한 PR을 계약 작업에 연결하고 검토 중으로 전환한다. PR은 사용자 Merge 전까지 제안 상태로 기록하고 해당 응답을 마친다.

## 머지 후 마무리

사용자가 “머지했어”처럼 해당 작업의 Merge 완료를 알리거나 마무리를 요청하면 [계약 작업 상태와 머지 후 마무리](../../../docs/workflows/orchestrator.md#계약-작업-상태와-머지-후-마무리)를 따른다. 연결된 PR의 실제 Merge와 공식 원본을 확인하고, 영향 작업의 기준을 갱신한 뒤 계약 작업을 완료 처리한다. 같은 요청에서 안전한 범위의 로컬 기준 브랜치 최신화와 작업 브랜치 정리를 수행한다.

`issue-refinement`가 필요하면 사용자에게 별도 실행을 안내하고 자동 호출하지 않는다. 제품 구현, 통합 영향 검토의 상태 갱신, 개발 사이클은 실행하지 않는다. 작업·PR의 실제 상태, 승인·미결·영향·검증, 공식 SHA, 브랜치 최신화·정리 결과와 재개 조건을 보고한다.
