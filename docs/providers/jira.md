# Jira 작업 추적 절차

이 절차는 선택 서비스의 `work_tracking.provider: jira`에만 적용한다. 공통 `AGENTS.md`, 공식 원본 조회·사용자 결정·PR 분석·통합 완료 기준은 유지한다. GitHub는 코드·PR·리뷰·CI, 설정된 Specs 저장소는 공식 명세의 원본이다. GitHub Projects의 Draft·Approval·Sub-issue 또는 자동 Ready 전환 절차를 Jira에 적용하지 않는다.

## 설정과 실행 전 확인

선택 서비스의 Jira 사이트·프로젝트를 확인하고, 실행할 작업과 단계에 필요한 설정만 읽어 실제 Jira 사이트·프로젝트·유형별 상태·우선순위 및 레이블 필드의 사용 가능 여부와 대조한다. 같은 상태의 중복 이름, 작업에 필요한 설정의 누락·잘못된 값, 조회·인증 실패, 필수 권한 또는 필요한 관계 지원 미확인은 해당 작업을 보류하고 보고한다. Jira 실패를 GitHub Projects로 대체하지 않는다.

- Backend·Frontend 개발은 아래 개발 Task 절차의 구현 유형·상태, 선택한 역할 라벨 및 그 단계에 필요한 설정을 확인한다. 상대 역할 라벨이나 후보 관리 설정은 요구하지 않는다.
- Orchestrator는 후보 등록·정제 등 요청된 작업에 필요한 `issue_types.candidate`, `statuses.candidate`, `statuses.backlog`, `approval`, `priority_order`와 구현 역할의 `role_labels` 등을 확인한다. 후보 승인 방식 `approval`은 `user_transition_to_backlog`만 지원한다. Epic 전환 또는 계약 작업에 필요한 `issue_types.epic`이나 `issue_types.contract`는 해당 작업이 필요한 경우 확인한다. 역할 레이블을 설정할 때 값과 작업 편집 권한을 확인한다. 기존 레이블 목록에 없다는 이유만으로 관리자에게 별도 사전 생성을 요구하지 않는다.

연결된 Atlassian 도구를 우선 사용하고 목록은 마지막 페이지까지 확인한다. Jira 작업의 쓰기 전에는 해당 작업에 필요한 조회·생성·수정 권한과 필수 필드·상태 전환 조건을 확인한다. Epic이 필요한 경우에만 후보 유형 전환과 Task 상위 관계의 지원·권한·필드 및 상태 매핑을 확인한다. 상태나 유형이 존재한다는 사실은 전환 가능성의 증거가 아니다. GitHub Project 편집 권한·Draft·공식 Sub-issue 확인은 요구하지 않는다. 설정 변경이나 Jira 관리자 권한이 필요하면 보고하고 임의로 설정하지 않는다. 토큰 등 비밀을 기록하지 않는다.

## 후보와 승인

`feature-discovery`는 공식 원본과 GitHub의 구현·열린/닫힌 Issue·PR, Jira의 기존 후보·작업·관계를 조회하여 중복을 확인한다. 확인이 실패한 범위는 부재로 간주하지 않는다. 요청당 최대 3개의 유효 후보를 설정된 후보 유형으로 생성하고 `statuses.candidate`에 둔다. 각 본문에 고유 Candidate ID, 목적·예상 효과·차이·미결 사항과 제안 출처를 남긴다. 생성 시 기본 상태가 다르면 가능한 전환을 확인해 후보 상태로 이동하고 실제 상태를 조회한다. 후보 생성·상태 설정은 승인이나 개발 착수가 아니다.

사용자가 후보를 `statuses.backlog`로 직접 옮기는 것을 후보 승인으로 사용한다. 자동 정제 전 상태 이력에서 후보에서 백로그로의 전환자·시각을 확인하고 그 전환자가 사용자임을 신뢰할 수 있는 계정 정보와 대조한다. 채팅 등 별도 출처에 있는 승인도 작성자·대상·범위를 확인해 기록한다. 현재 상태만으로 승인자나 승인 범위를 추정하지 않는다. 이력·사용자 식별·승인 출처를 확인할 수 없으면 해당 후보는 보류한다. 승인 후 다시 후보 상태로 돌아갔다면 최신 전환과 승인 유효성을 다시 확인한다.

## 공식 계약 변경과 차단 관계

요청된 작업 범위에서 구현 Task가 공식 계약 변경을 실제 선행 조건으로 필요로 한다고 확인되면, 별도 확인을 반복하지 않고 해당 계약 변경 Task가 구현 Task를 차단하는 Jira 이슈 관계를 등록한다. 일반적인 구현 작업 간 순서나 계약과 무관한 선행 작업에는 자동으로 차단 관계를 만들지 않고 관련 Task 본문의 선행 조건 또는 완료 조건에 기록한다. 기존 관계는 임의로 삭제·변경하지 않는다. 계약에 의존하는 범위와 이유, 해제에 필요한 조건을 구현 Task에 기록한다. 작업의 일부에만 의존성이 있으면 그 범위를 명시하고, 작업 전체의 착수·완료를 막는 관계인지 확인한다. 범위나 방향이 불명확하면 추측하지 않고 사용자와 협의한다.

등록 전 양쪽 작업과 기존 관계, 관계 유형·방향, 연결 권한 및 순환 여부를 확인한다. 동일 관계는 재사용하고 반대 방향·충돌·권한 또는 조회 실패는 보류해 보고한다. 연결 후 계약 변경 Task의 `blocks`와 구현 Task의 `is blocked by`를 양쪽에서 재조회한다. 쓰기 결과가 불명확하면 재조회하기 전 중복 등록하지 않는다. 계약 방향과 영향이 충분히 명확하면 명세 PR 전에 필요한 기존 구현 작업을 재사용하고, 없는 경우 중복·유형·필수 필드·생성 권한을 확인해 구현 Task를 생성한다. 제안된 범위, 공식 Merge 전 선행 조건과 기존 공식 기준을 명시하고 해당 관계를 연결한다. 필요성·대상·관계가 불명확하면 추측해 생성하거나 연결하지 않고 미결 조건을 기록한다. 계약 변경 Task의 완료만으로 계약이 반영됐다고 판단하지 않고 필요한 공식 명세가 설정된 원본의 기본 브랜치에 실제로 Merge됐는지 확인한다.

차단 여부를 복제하는 별도 라벨은 기본적으로 추가·제거하지 않는다. Jira 관계와 선행 작업 상태 및 후행 작업에 기록된 해제 조건을 기준으로 판단하며, 이슈 관계의 존재나 선행 작업의 종료만으로 현재 차단 여부가 자동 갱신된다고 가정하지 않는다. 작업 상태를 자동 전환하거나 기존 라벨을 임의로 변경하지 않는다. 분석 전용·등록 제외 등 사용자 범위 제한과 각 Skill의 쓰기 경계를 우선한다.

## 정제·연결

`backlog-refinement`는 백로그 상태 작업을 끝까지 조회하고 Candidate ID, 제안 출처와 상태 이력으로 후보를 식별해 일반 구현·계약 Task와 구분한다. 후보 여부를 확인할 수 없는 작업은 보류한다. 사용자 승인 이력을 확인한 후보만 대상으로 최대 2개를 선정한다. 지정 후보를 우선하고 중복·목표·우선순위·의존성·공식 원본을 확인한다. 나머지는 실제 선행 관계와 `priority_order`를 따르고 동률은 생성 시각이 오래된 순, 다시 같으면 안정적인 이슈 ID 순으로 선정한다. 우선순위가 없으면 마지막에 두고 설정에서 해석할 수 없는 값이나 순환 의존성은 보류한다. 가능한 후보가 부족하면 채우지 않는다. 목표나 승인·의존성이 불명확하면 보류하고, 세부 결정이 남은 경우 질문과 함께 백로그에 둔다. 같은 요청의 부분 성공 재개도 최대 2개에 포함한다. 새 후보 등록이나 승인 변경은 수행하지 않는다.

후보의 키·목적·범위·제외·완료 조건·공식 원본 URL과 SHA·승인 이력을 보존한다. 독립 추적할 구현 작업의 수와 기능 전체의 완료를 함께 판단할 필요를 기준으로 아래 중 하나를 선택한다. Backend·Frontend 구분 자체는 Epic 생성 기준이 아니다. 실제 담당 저장소와 역할, 독립 실행 조건, 계약 참조·미결 조건을 본문에 기록한다. 정제와 상세화 단계는 별도 레이블을 만들지 않고 작업 종류와 본문의 체크리스트로 구분한다.

- 독립적으로 추적할 구현 작업이 하나면 기존 후보를 같은 키의 `issue_types.implementation` Task로 유지하고 해당 역할 라벨·구현 범위·완료 조건을 추가한다. 별도 구현 Task나 Epic을 만들지 않는다. 후보 유형이 구현 Task가 아니면 같은 키로 변경 가능한지 확인하고 불가능하면 보류한다.
- 여러 구현 작업을 따로 추적하고 기능 전체의 완료를 함께 판단해야 하면 기존 후보를 같은 키의 `issue_types.epic`으로 전환한다. 그 아래 필요한 구현 Task만 생성하거나 기존 Task를 재사용하고 역할 라벨을 붙인다. 기존 후보를 자식으로 남기거나 별도의 대체 Epic을 만들지 않는다. 여러 작업이지만 통합 완료 판단이 필요한지 불명확하면 구조를 추정하지 않고 보류한다.

후보 본문의 정제 체크리스트에 필요한 역할·작업·관계별 결과를 기록한다. 정제 완료 후보는 자동 선정에서 제외하고, 부분 성공 후보는 실제 작업·관계를 재조회한 뒤 남은 단계부터 재개한다. 기존 후보의 완료 여부가 불명확하면 임의로 새 작업을 만들지 않고 확인한다. 사용자 후보에 Candidate ID가 없으면 기존 Jira 이슈 키를 안정 식별자로 사용한다.

Epic 전환 전 같은 프로젝트·같은 키 유지, 현재 상태와 대상 상태, 필수 필드, 기존 본문·승인 이력·첨부·관계 보존 및 전환 권한을 확인한다. 도구가 미리보기나 별도 확인을 요구하면 그 절차를 따르고, 지원 여부·보존·결과가 불명확하거나 전환이 실패하면 별도 Epic으로 우회하지 않는다. 사용자가 수동으로 같은 키를 전환하고 재개할 수 있는지 확인하거나 해당 작업을 보류한다. 전환 후 원래 키·유형·상태·보존 항목을 재조회한다. 필요한 Task를 Epic의 자식으로 연결한 뒤 각 자식의 상위 항목과 Epic의 자식 목록을 양쪽에서 재조회한다. 다른 상위 항목이나 기존 관계를 임의로 교체하지 않는다.

구현 Task는 `statuses.backlog`에 둔다. 생성 기본 상태가 다르면 전환 가능 여부를 확인해 백로그로 이동하고 결과를 확인한다. `statuses.ready`로 이동하지 않는다. 자식 생성 전후 Candidate ID와 `Link Key: <후보 URL>|<대상 저장소>|<작업 식별자>`로 기존 작업을 확인하고 중복을 피한다. 쓰기·유형 전환 결과가 불명확하면 원래 키의 실제 유형·작업·관계를 재조회하고 이미 성공한 단계를 반복하지 않는다. 관계 조회 실패는 미연결이 아니다.

### 선택적 Confluence 기능 기획

이 절은 `backlog-refinement`의 Jira 후보 정제에만 적용한다. 설정 대상은 공통 루트의 Specs 우선·단일 구현 대상 규칙을 따르며 다른 저장소의 설정을 합치거나 대체하지 않는다. 선택 서비스의 `confluence`가 없거나 `enabled: false`이면 Confluence를 조회·변경하지 않고 Jira 정제만 진행한다. `enabled: true`이면 비어 있지 않은 `site_url`, `space_key`, `parent_page_id`가 필요하다. `site_url`은 Confluence 사이트의 `/wiki` 기본 URL이며 `parent_page_id`는 숫자 문자열이다. `enabled` 누락·잘못된 형식이나 필수 값 누락은 Confluence 부분만 보류하고 Jira 정제 결과와 본문 초안을 보고한다. 다른 값을 추측하거나 다른 대상 설정으로 대체하지 않는다.

승인된 후보 중 사용자 흐름·기능 범위·결정 논의를 문서로 유지할 필요가 있는 기능만 대상으로 한다. 기술 작업이나 기존 문서가 충분한 작업에는 불필요한 페이지를 만들지 않는다. 사용자의 분석 전용·문서 생성 제외·특정 위치 지정 등 명시적 제한을 우선한다. 필요 여부가 불명확하면 추측해 페이지를 만들지 않고 이유와 초안을 보고한다.

페이지 쓰기 전 설정된 사이트와 공간, 상위 페이지가 실제로 일치하고 접근 가능한지, 조회·생성·수정 및 Jira 웹 링크에 필요한 권한을 확인한다. `space_key`는 현재 활성 스페이스 키를 사용한다. Confluence가 변경 전 원래 `key`와 현재 `currentActiveAlias`를 함께 반환하면 현재 별칭과 스페이스 ID를 대조하고 상위 페이지의 스페이스 ID도 같은지 확인한다. 현재 키를 확인할 수 없거나 식별자가 충돌하면 보류한다. 확인 실패는 부재가 아니며 다른 공간·상위 페이지를 자동 선택하지 않는다. Jira 키·Candidate ID와 기존 Jira 웹 링크 및 Confluence 검색을 끝까지 확인해 기존 페이지를 찾는다. 같은 기능의 페이지가 하나면 재사용하고, 여러 개이거나 소유 관계가 불분명하면 생성·수정을 보류한다. 기존 페이지는 최신 본문·버전과 사용자 변경을 보존하고 정제에 필요한 범위만 반영하며, 공식 계약이나 이미 확정된 결정을 임의로 바꾸지 않는다.

기능 기획 페이지에는 목적·사용자 흐름·범위·완료 조건·미결 사항, 관련 Jira 키와 공식 원본 URL·조회 SHA를 담고 초안과 확정 결정을 구분한다. Jira는 작업 상태와 완료 조건, Confluence는 기획과 논의를 관리한다. 요구사항·API·인증·ERD·UI의 공식 기준은 설정된 저장소 원본이며 Confluence가 이를 대체하지 않는다. 새 페이지는 확인된 상위 페이지 아래에 생성한다.

기능을 묶는 Epic이 있으면 Epic을, 독립 단일 작업이면 그 Task를 기획 페이지의 기준 Jira 작업으로 삼는다. 후보가 Epic으로 전환되면 원래 키를 유지하므로 같은 작업에 링크한다. 기준 작업에 페이지의 일반 웹 링크를 추가하고 페이지에는 기준 작업 링크를 넣는다. 기존 링크는 재사용하며 Confluence 콘텐츠 전용 관계라고 주장하지 않는다. 양쪽을 재조회해 페이지 ID·URL, 상위 페이지, 기준 Jira 키, 본문과 링크를 확인한다. Jira와 Confluence의 본문·상태가 자동 동기화된다고 가정하지 않는다. 생성이나 연결 결과가 불명확하면 페이지 ID·Jira 키·링크를 먼저 재조회하고 재생성하지 않는다. 페이지 생성·수정 또는 링크가 부분 실패하면 성공한 부분과 보류 사유를 Jira 정제 체크리스트와 결과에 기록하고 재개 시 기존 결과를 재사용한다. 실패가 Jira 정제 성공이나 Confluence 문서 완성을 뜻하지는 않는다.

## 상세화 논의의 Confluence 기록

선택 서비스의 `confluence.enabled: true`이면 `issue-refinement`는 지정 작업의 실제 상위 관계를 확인하고 지정 작업과 확인된 상위 작업의 웹 링크 및 Confluence 검색을 끝까지 확인해 해당 기능의 기존 페이지를 찾는다. 기능을 묶는 Epic이 있으면 Epic을, 독립 단일 작업이면 그 Task를 기획 페이지의 기준 Jira 작업으로 삼는다. 자식 Task의 상세화에서 처음 생성하더라도 같은 Epic의 기능 기획 페이지는 Epic을 기준으로 공유한다. 상위 관계를 확인하지 못하면 단일 작업으로 추정하지 않는다. 연결된 페이지가 없다는 사실만으로 해당 페이지가 존재하지 않는다고 판단하지 않는다. 기존 페이지가 하나이고 소유 관계가 명확하면 재사용한다. 여러 페이지가 후보이거나 소유 관계가 불명확하면 임의 선택·생성하지 않고 보류한다. 조회 실패도 부재가 아니다.

기존 페이지가 없고 사용자 흐름·기능 범위 또는 결정 논의를 문서로 유지할 필요가 명확하면, 선행 백로그 정제 여부와 무관하게 설정된 상위 페이지 아래에 기능 기획 페이지를 생성한다. 기존 문서로 충분하거나 별도 기획 기록이 불필요한 기술 작업은 새 페이지를 만들지 않는다. 필요성이나 대상이 불명확하면 이유와 초안을 보고한다. 생성 전 `site_url`, `space_key`, `parent_page_id`의 유효성, 실제 사이트·현재 활성 공간·상위 페이지의 일치와 조회·생성·수정·Jira 웹 링크 권한을 위 Confluence 기능 기획 절차에 따라 확인한다. 다른 위치나 설정을 추측하지 않는다.

재사용 또는 생성한 페이지에는 상세화 대화에서 결론에 영향을 준 제안·대안·이유, 사용자가 확인한 판단과 출처, 선행 조건 및 남은 질문을 기록한다. 협의·결정 기록은 기존 기획 내용 아래에 구분선을 두고 별도 영역에 배치한다. 이미 같은 기록 영역이 있으면 재사용하고 기존 내용과 이력을 보존하며 구분선을 반복 추가하지 않는다. 필요한 목적·사용자 흐름·범위·완료 조건과 공식 원본 URL·조회 SHA, 관련 Jira 작업을 포함한다. 협의가 진행 중이라도 확인된 내용과 미결 사항을 구분해 반영하며, 권장안이나 제안 이유를 사용자의 승인·사용자가 밝힌 이유로 추정하지 않는다. 실제 영향받는 기능과 작업 범위에만 반영하고, 차단 관계의 의미 및 필요한 계약의 공식 반영 전 보류 범위를 구분한다.

최신 페이지 본문·버전과 기존 결정을 확인하고 기존 내용·사용자 변경을 보존한다. 이미 결정된 항목이 미결로 보이지 않게 현재 결정과 남은 질문을 갱신하되 이력은 보존한다. 대상과 쓰기 권한이 확인되면 별도 승인을 반복하지 않고 반영한다. 기준 Jira 작업에는 페이지 일반 웹 링크를, 페이지에는 기준 작업 링크를 추가하고 기존 링크는 재사용한다. 기존 자식 Task의 링크는 보존하되 자식마다 별도 페이지를 만들지 않는다. 생성·수정 후 페이지 ID·URL·상위 페이지·본문·버전과 기준 작업의 Jira 링크를 양쪽에서 재조회한다. 연결·접근·권한·쓰기 실패 또는 결과 불명은 정보 부재나 완료로 간주하지 않고 성공한 단계와 보류 지점을 Jira 결과와 구분해 보고한다. 재개 시 현재 페이지와 링크를 먼저 확인하고 중복 생성·연결하지 않는다.

`confluence` 설정 생략 또는 `enabled: false`이면 기본적으로 Confluence 조회·변경을 수행하지 않는다. 활성 설정이 유효하지 않거나 페이지를 확인할 수 없으면 해당 기록만 보류하고 Jira 상세화 결과와 기록 초안을 보고한다. 사용자의 명시적 페이지 지정, 분석 전용 또는 문서 변경 제외 지시를 우선한다. Confluence는 기능 기획·논의 기록이며 공식 계약이나 Jira 상태와 자동 동기화되는 원본이 아니다.

## 계약 변경 협의의 Confluence 기록

`contract-management`는 Jira 댓글을 작성하지 않는다. Jira 계약 작업과 영향받는 작업의 본문에는 필요한 상태·영향·승인 범위·미결 사항과 공식 원본 URL·SHA 및 논의 페이지 링크를 간결히 반영한다. 협의 과정과 결정의 상세 기록은 연결된 Confluence 페이지에 둔다. 협의가 진행 중이어도 사용자 결정을 확인한 범위부터 반영하고, 근거·대안·권장안과 사용자의 선택을 구분한다. 명세 수정 승인은 별도로 확인하며, 계약 작업의 등록이나 페이지 작성은 승인이 아니다.

사용자가 페이지를 지정하거나 Confluence 사용을 요청한 경우 그 지시를 우선한다. 그렇지 않고 `confluence.enabled: true`이면 계약 작업의 웹 링크와 Confluence 검색으로 같은 계약 논의 페이지를 확인한다. 소유 관계가 명확한 기존 페이지는 재사용한다. 새 페이지가 필요하고 `confluence.contract_parent_page_id`가 설정돼 있으면 확인된 사이트·공간의 해당 상위 페이지 아래에 생성한다. 이 값은 기능 기획용 `parent_page_id`와 별개다. 계약 페이지의 위치가 지정되지 않았거나 모호하면 임의로 기능 기획 상위 페이지에 생성하지 않고 해당 기록을 보류·보고한다. 설정 생략 또는 `enabled: false`는 기본적으로 Confluence 미사용이며 Jira 협의를 막지 않는다.

새 페이지 생성 전 사이트·현재 활성 공간·상위 페이지·중복·생성 권한을 확인한다. 최신 본문과 이력을 보존하며, 계약 작업에 페이지의 웹 링크를 추가하고 페이지에 계약 작업·관련 기능 페이지·원본을 연결한다. 기존 검토 내용 아래에 구분선을 두고 협의·결정 기록 영역을 구분한다. 해당 영역에는 논의의 선택지·권장 이유, 확인된 사용자 결정과 출처, 남은 질문을 간결히 정리하고 협의가 진행될 때 갱신한다. 이미 같은 영역이 있으면 재사용하고 기존 내용을 덮어쓰거나 구분선을 반복 추가하지 않는다. 영향을 받는 기존 기능 기획 페이지가 명확하고 쓰기가 요청 범위에 포함되면 계약 작업과 논의 페이지, 해당 기능에 필요한 영향·선행 조건을 간결히 연결한다. 명세 PR이 생기면 PR 링크와 미병합/병합 상태를 관련 기록에 반영하고, 실제 Merge 뒤에만 공식 기준 SHA를 갱신한다. 설계 결정 기록은 다른 기능에 재사용할 가치가 있으면 짧은 초안을 제안하며, 생성·수정은 사용자 요청 범위를 따른다.

기존 링크와 페이지를 재사용하고 변경 후 페이지·Jira 링크와 영향을 받은 기록을 재조회한다. 접근·권한·대상 확인 실패나 결과 불명은 부재나 성공으로 간주하지 않는다. Confluence 기록이 보류돼도 Jira 댓글을 대체 기록으로 작성하지 않고 성공한 단계와 미기록 내용을 보고한다. 재개할 때 실제 상태를 재조회한다. Confluence는 논의 기록이며 공식 계약이나 Jira와 자동 동기화되는 원본이 아니다.

## 상세화·계약·착수

`issue-refinement`는 지정된 Jira 작업과 검증된 관련 관계·결정·의존성·GitHub PR 및 공식 원본 URL·SHA를 확인한다. 단일 구현 작업이면 해당 Task에 결정·공식 계약 URL과 SHA·구현 범위·완료 조건·선행 조건·미결 사항을 반영한다. Epic으로 묶인 경우 Epic에는 기능 전체의 공통 결정만, 관련 Task에는 각 구현 범위·완료 조건과 필요한 계약 참조·선행 조건·미결 사항을 반영한다. 기존 이력과 관계를 보존한다. 필요한 계약 변경 작업은 `issue_types.contract`로 기존 Jira 작업을 확인해 재사용하거나 생성하고 관련 작업과 상호 참조한다. 관련 참조를 Epic 상위 관계로 오인하지 않는다. 계약 변경 작업 등록은 명세 변경 승인이 아니다.

상세화 결과와 미결 조건을 사용자에게 보고한다. 후보 승인은 착수 승인이 아니다. 필수 조건과 사용자의 결정이 갖춰져도 Orchestrator는 구현 Task를 `statuses.ready`로 옮기지 않는다. 사용자가 실제 착수할 Task를 직접 옮긴다. 이미 진행 중인 상태를 덮어쓰지 않는다. 다른 Skill이나 개발은 자동으로 시작하지 않는다.

`contract-management`는 사용자의 직접 요청에서 독립 실행하고 Jira 계약 작업에 결정·영향·공식 원본을 기록한다. 승인된 변경만 공식 Specs 저장소의 PR로 제안하고 실제 Merge 전까지 공식 원본으로 취급하지 않는다. `change-impact-review`는 Jira 작업·관계를 조회해 재사용이나 후속 작업을 제안하되 검토 요청만으로 생성·상태 변경하지 않는다.

## 개발 착수·재개·완료

개발 Skill은 `docs/workflows/development.md`와 이 문서의 개발 절차를 따른다. 신규 착수는 사용자가 Ready로 옮긴 해당 역할 Task를 확인하고 In Progress로 전환·재조회한다. 검토 가능한 PR URL을 같은 Task에 남기고 In Review로 전환·재조회한다. 재개 시 In Review를 In Progress로 되돌리지 않는다. 사용자가 마무리를 요청하면 연결 PR이 설정된 해당 대상 저장소와 기준 브랜치에 실제 머지됐는지 확인한 뒤 그 Task만 Done으로 전환하고 재조회한다. 확인 실패나 복수 PR의 모호함은 보류한다. PR 머지는 사용자가 직접 한다. Jira Automation이나 자동 Epic 완료를 설정하거나 가정하지 않는다. 개별 Task 완료는 기능 전체의 완료가 아니다.

## 설정과 선정

활성 서비스의 `jira.site_url`, `project_key`, `issue_types.implementation`, `statuses.ready`, `statuses.in_progress`, `statuses.in_review`, `statuses.done`, 선택한 구현 역할의 저장소와 기준 브랜치를 해당 작업·단계에 필요한 범위에서 확인하고 실제 Jira 프로젝트·유형·상태·라벨·접근 권한과 대조한다. 자동 선정 시 `priority_order`도 확인한다. 역할 라벨은 Backend 작업이면 `jira.role_labels.backend`, Frontend 작업이면 `jira.role_labels.frontend`만 확인하며 상대 역할의 라벨을 필수로 요구하지 않는다. `issue_types.candidate`, `statuses.candidate`, `statuses.backlog`, `approval`이 없어도 나머지 착수 조건을 충족하는 `ready` 상태의 구현 Task를 진행할 수 있다. 상태 이름이 중복되거나 작업에 필요한 값·권한·전환을 확인할 수 없으면 보류한다. Jira 연결 도구를 우선 사용하고 목록의 모든 페이지를 확인한다. 상태 존재만으로 전환 가능하다고 가정하지 않는다. 비밀값은 기록하지 않는다.

새 작업을 선정할 때는 설정된 프로젝트에서 유형이 `jira.issue_types.implementation`인 Task 중 상태가 `jira.statuses.ready`이고 선택한 역할에 해당하는 `jira.role_labels.backend` 또는 `jira.role_labels.frontend` 라벨이 있는 작업만 선정한다. 새로 직접 지정한 작업도 같은 조건을 확인한다. Epic, 후보, 다른 역할이나 다른 프로젝트는 제외하며 조건을 확인할 수 없는 작업은 보류한다. 사용자가 직접 `ready`로 옮기며 개발 Skill은 이 전환을 수행하지 않는다. 기존 작업의 재개에는 `ready`를 요구하지 않고 아래 재개 절차를 따른다.

기존 진행 작업이 있으면 새 작업을 시작하지 않는다. 후보의 본문·사용자 결정과 출처·관련 관계 및 선행 조건을 확인하고 미결정 또는 충족 여부가 불명확하면 보류한다. 선행 작업이 열려 있으면 제외하며 조회 실패를 관계 없음으로 취급하지 않는다. 가능한 후보는 `jira.priority_order`의 순서, 생성 시각이 오래된 순, 안정적인 이슈 ID 순으로 선정한다. 우선순위가 없으면 마지막에 두고 설정에 없는 우선순위는 보류한다. Jira 키·제목·선정 근거와 결정 출처를 기록해 기존 설계·품질 게이트에 전달한다.

## 상태와 PR

1. 새 작업의 실제 착수 직전에 해당 Task의 프로젝트·유형·라벨·현재 `jira.statuses.ready` 상태와 가능한 전환을 다시 확인한다. `jira.statuses.in_progress`로 전환하고 같은 Task를 재조회해 결과를 확인한다. 실패하거나 결과가 불명확하면 재조회해 이미 성공한 변경을 반복하지 않고, 확인되지 않으면 중단한다. 재개에서는 이 신규 착수 전환을 반복하지 않는다.
2. 설정된 선택한 구현 역할 저장소와 대상 브랜치로 검토 가능한 PR을 연 후 해당 Task에 PR URL을 기록한다. Task를 재조회해 정확한 링크가 남았는지 확인한 뒤 `jira.statuses.in_review`로 전환하고 다시 조회한다. 링크나 상태 확인에 실패하면 중단하고, 재개 시 이미 기록된 링크·상태를 확인해 중복 기록을 피한다.
3. 사용자의 작업 마무리 요청을 받았을 때만 Task에 연결된 PR을 GitHub에서 조회한다. PR의 저장소와 대상 브랜치가 설정된 선택한 구현 역할 저장소·기준 브랜치와 일치하고 실제 merge된 사실을 확인한다. 닫힘이나 머지 예정만으로 완료 처리하지 않는다. 연결된 PR이 여러 개이거나 대상이 불명확하면 추측하지 않고 확인한다. 확인된 해당 Task만 `jira.statuses.done`으로 전환하고 재조회한다. 전환 불가·조회 실패·불일치는 중단해 보고한다.

전환 전 현재 상태·가능한 전환·필요 권한을 확인하고, 각 쓰기 후 실제 결과를 확인한다. 기존 완료 상태라면 변경을 반복하지 않는다. Jira Automation은 설정하거나 성공했다고 가정하지 않는다. PR 머지는 사용자가 직접 수행하며 Task 완료는 Epic이나 기능 전체의 완료를 의미하지 않는다.

## 범위와 재개

### 기존 작업 재개

작업 기록을 단서로 같은 Task의 프로젝트·유형·선택한 구현 역할 라벨·현재 상태와 연결된 PR, Git 브랜치·변경 사항을 재조회한다. 기존 작업임을 확인할 수 없거나 상태·PR·기록이 충돌하면 보류하고 보고한다. `jira.statuses.in_progress`에서는 상태 변경 없이 남은 작업을 이어간다. `jira.statuses.in_review`에서는 `in_progress`로 되돌리지 않고 기존 PR의 리뷰·수정·검증을 이어간다. PR이 실제 머지됐다면 사용자의 마무리 요청을 기다리고 위 완료 절차를 따른다. 그 밖의 상태나 PR 연결이 불명확하면 추측해 변경하지 않는다. 동시 실행을 막는 잠금이나 원자적 선점은 제공하지 않는다.


## 계약 변경 발견

기존 계약을 지키는 대안을 먼저 검토한다. 변경이 필요하면 관련 작업을 보류하고 공식 원본 링크와 확인 버전, 사유·대안과 한계·영향·수정안·필요한 결정을 로컬 `docs/current-work-log.md`에 기록하고 사용자에게 보고해 별도 계약 변경 절차로 안내한다. 이 사유를 기록하려고 Jira Task 본문이나 댓글을 수정하지 않는다. 실제 공식 원본 반영과 사용자 결정, 설계·검증을 재확인한 뒤 재개한다.
