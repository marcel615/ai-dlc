# 통합 검증과 완료 판정

각 항목은 **통과·실패·보류·대상외** 중 하나로 판정하고 근거를 기록한다. 대상외는 이유가 필요하며, 미실행·자료 부족은 통과가 아니다.

## 기능·설정·공식 관계

- provider가 없으면 기존 `github_projects`로 해석했고, Jira를 명시한 경우 설정·접근 실패를 다른 도구로 대체하지 않았다.
- Jira에서는 후보 승인자의 전환 이력과 출처를 확인하고 구현 Task의 `ready` 전환은 사용자에게 남겼다. 단일 구현 작업은 원래 후보 키의 Task로 유지하고, 여러 작업의 통합 완료 판단에 필요한 경우에만 같은 키로 Epic 전환 후 자식 관계를 양쪽에서 확인했다.
- 백로그 정제와 이슈 상세화에서 공식 UI를 포함한 관련 원본을 현재 범위·확정 동작과 대조하고, 변경 필요 여부·근거·기준 SHA를 기록했다. 필요한 Specs 작업은 중복 확인 후 재사용하거나 등록했고 Jira에서 담당 라벨과 초기 상태를 확인했다.
- Jira 차단 관계는 명세 병합을 실제로 기다려야 하는 구현 Task와 기능 전체 완료에 명세 병합이 필요한 Epic에 연결했다. 의존 범위·이유·해제 조건과 중복·방향·권한·순환을 확인한 뒤 양쪽에서 재조회했다. 병행 가능한 표기 정정은 관련 작업으로 추적했다. 기존 관계와 작업 상태를 보존하고 공식 명세의 실제 Merge로 해제 조건을 확인했다.
- Jira 백로그 정제의 Confluence 설정이 없거나 비활성이면 문서 조회·변경 없이 Jira만 처리했다. 활성 설정에서는 확인된 사이트·공간·상위 페이지와 기능 문서의 필요성·중복·권한을 확인했다. 생성·재사용한 페이지의 Jira 링크와 Jira 웹 링크를 양쪽에서 재조회하고, 실패·부분 성공은 성공과 구분해 재개 지점을 보고했다. Confluence 기획을 공식 요구사항·계약이나 자동 동기화된 상태로 취급하지 않았다.
- Jira 백로그 정제·이슈 상세화·계약 변경 관리에서 새 Confluence 페이지를 만들었다면 사용자 지정 제목이 없는 한 확인된 기준 Jira 키를 제목 앞에 붙였다. 기능 기획은 Epic 또는 독립 Task, 계약 논의는 계약 변경 Task를 기준으로 삼았다. 키가 없는 기존 제목도 중복 확인에 포함하고 제목 형식만으로 기존 페이지를 변경하거나 새로 만들지 않았다.
- Jira 정제·상세화의 기능 기획 페이지는 실제 Epic이 있으면 Epic을, 독립 단일 작업이면 해당 Task를 기준으로 양방향 연결했다. 자식 Task에서 처음 상세화할 때도 상위 관계와 공유 페이지를 확인하고 중복 생성을 피했다. 상세화에서는 선행 백로그 정제를 요구하지 않고 결론에 영향을 준 제안·대안·이유, 사용자 판단·출처와 미결 질문을 기존 기획 아래 구분선으로 분리해 기록하고 재조회했다. 기존 기록 영역을 재사용하고 이력과 사용자 변경을 보존했으며 대상·중복·권한이 불명확할 때 임의 생성·선택하지 않았다. 접근·쓰기 실패나 결과 불명은 성공한 단계 및 Jira 결과와 구분해 보고했다.
- 아래 Draft·GitHub 저장소 Issue·공식 Sub-issue·Project 필드 항목은 `github_projects`에 적용한다. Jira에는 `docs/providers/jira.md`의 해당 검증을 적용한다.

- 공통 운영 루트와 유일하게 식별한 대상 프로젝트 루트·설정·실제 Git 원격을 확인하고 대상 로컬 지시와의 충돌을 확인했다. 상대 상태 파일 경로는 대상 루트를 기준으로 해석했다.
- 선택 서비스와 설정 버전을 확인했다. 공통 Parent가 필요한 경우 설정된 관리 저장소에 있고, 단일 저장소 Draft 직접 전환의 경우 불필요한 Parent를 강제하지 않았다.
- 공통 후보 제안은 `feature-discovery`의 최대 3개 Pending Draft 범위를 따르고, 정제는 `backlog-refinement`에서 실제 Approved 후보만 처리했다. 기존 사용자 후보도 승인·식별자를 확인해 재사용하며 선행 Skill 실행 자체를 완료 요건으로 삼지 않았다.
- 자동 정제는 실제 Approved Draft에서 중복·미결정·우선순위·선행 관계를 검토해 최대 2개 선정했고 지정 후보를 우선했다. 보류·제외·기존 작업 재사용 근거를 보고했다.
- 제안·승인·정제·개발을 구분하고 다른 Skill이나 다음 개발 사이클을 자동 실행하지 않았다.
- 필요한 구현 작업만 해당 저장소에 존재한다. 한쪽만 필요한 이유와 미연결 역할의 미검증을 구분했다.
- Parent/Sub-issue 관계가 필요한 경우 실제 Issue ID로 양방향 조회했다. URL만 있는 상태를 연결 완료로 처리하지 않았다.
- 동일 Issue 생성·관계 중복 추가가 없고, 다른 Parent의 작업을 임의 재배치하지 않았다.
- 해당 Issue와 필요한 Parent·Sub-issue의 Project 등록·필드·상태 매핑을 확인했다.
- 권한·원본·공식 관계 조회 실패를 부재로 취급하지 않았다.
- Issue 상세화에서는 사용자 결정·출처, 공식 원본 SHA, 미결 조건과 명시적 착수 승인을 구분했다. 자식의 개발 상태와 기존 관계를 보존했다.
- 계약 변경 Issue는 범위·중복·Project 등록을 확인하고 관련 Issue와 상호 참조했다. 참조를 공식 Sub-issue 관계로 오인하지 않았다.
- 계약 변경 협의에서 결정 항목별 대안·권장 이유와 사용자의 실제 판단·출처·미결 사항을 구분해 기록했다. Jira 댓글을 작성하지 않았고, Confluence 사용 시 협의·결정 영역을 기존 검토 아래 구분선으로 분리했다. 대상·권한 확인과 부분 실패를 보고하고 개별 결정과 명세 수정 승인을 혼동하지 않았다.
- 계약 변경 방향이 명확한 경우 명세 PR 전 구현 영향과 기존 작업을 확인해 재사용하거나 필요한 누락 작업만 생성·연결했다. 제안과 공식 Merge를 구분하고 선행 조건·기준 SHA·재상세화 필요성을 기록했다.
- 계약 작업의 조회·등록을 provider별로 구분했다. Jira에서는 기존 계약 Task를 먼저 확인해 재사용하고 없을 때만 생성했으며, GitHub Issue 생성·Project 등록은 `github_projects`에서만 수행했다. Jira에서도 영향 확인을 위한 GitHub 조회와 승인된 Specs PR 생성을 유지했다.
- 계약 변경 중 신규 Jira 구현 Task는 설정된 구현 유형·담당 역할 라벨·백로그 상태와 중복 확인 규칙을 적용하고 결과를 재조회했다. 기존 Task의 진행 상태와 라벨을 보존하고 `ready` 전환은 사용자에게 남겼으며 후보 승인 절차를 추가로 요구하지 않았다.

## 계약과 호환성

- 공식 요구사항·API·인증·ERD·UI의 설정 역할·기본 브랜치·경로를 실제 조회하고 원본 URL·commit SHA를 확인했다. 과거 `reference_commit`을 현재 버전으로 고정하거나 다른 저장소의 SHA를 적용하지 않았다.
- 구현 저장소에 남은 명세 사본을 공식 원본으로 취급하거나 공식 원본 조회 실패를 사본으로 대체하지 않았다.
- `templates/orchestrator/docs/`의 초기 작성 양식을 확정된 공식 명세로 취급하지 않았다. 실제 공식 명세는 설정된 원본에서 확인했다.
- Parent와 구현 작업은 공식 원본의 관련 URL·SHA를 참조하며 기능별 범위·완료 조건·결정을 관리하고 세부 명세를 불필요하게 복제하지 않았다.
- method/path·필수 입력·응답·오류·의미·권한과 쿠키·CSRF·CORS·토큰 수명·회전·실패 처리를 필요한 범위에서 확인했다.
- 원본 담당·소비자 검토·통합 조정·사용자 결정 책임이 명확하며 비호환 변경의 전환 순서를 확인했다.
- 원본과 구현 불일치는 해결하거나 사용자 판단 전까지 보류했다.
- 계약 변경은 사용자 승인 범위만 명세 PR에 반영했고 PR과 실제 Merge 후 공식 원본을 구분했다. 관련 Issue별 영향·재상세화 판정과 보류 근거를 기록했다.
- ERD의 관계·제약과 구현 엔티티·마이그레이션의 영향을 필요한 범위에서 확인했고 중요한 DB 결정은 사용자에게 남겼다.
- UI 명세의 화면·경로·사용자 동작·공통 상태 처리와 Frontend 구현을 필요한 범위에서 대조했다. API·인증·데이터 구조는 각 공식 명세와 일치하며 미결정 UX를 임의 확정하지 않았다. 관련 UI 원본의 추가·변경은 분석 맥락에 포함해 재사용 여부를 판단했다.
- PR 탐색의 저장소별 기준 시점·조회 범위·실패 구간·이력과 분석 버전을 확인했다. 동일 맥락의 완료 분석만 재사용하고 새 head·base·공식 원본의 위치·요구사항·계약·소비자·결정 변경이나 보류 건은 재검토했다. 이전 분석이 현재 설정과 다른 명세 원본을 기준으로 수행되었다면 현재 공식 원본을 기준으로 재검토했다.

## 구현·통합 증거·재개

- 필요한 PR의 실제 Merge·Issue 종료 사유·대상 head의 CI·리뷰 결과를 확인했다. `not planned`는 구현 완료가 아니다.
- PR 본문의 성공 보고와 직접 조회한 실행 결과를 구분했다.
- Parent 완료 조건에 검증 환경·배포 필요 여부가 명확하고, 필요한 조합의 BE/FE commit·계약 SHA·검증 날짜·결과·증거가 있다.
- 인증은 영향 범위에 따라 로그인·재발급·로그아웃, CSRF·경합·탭 조정·401/403/503·응답 유실을 확인했다.
- 자식 완료율·자동 close·Project 자동화가 통합 검증 전 Parent를 완료 처리하지 않는지 확인했다.
- 부분 실패 재개에서 이미 생성된 Issue·공식 관계를 재사용하고 남은 단계만 수행했다.
- 남은 작업이 완료 조건을 막지 않는 이유와 제외 결정 출처가 명확하다.

## 보고

대상·시점·서비스·Issue/PR·계약 SHA, 단계별 실제 결과, 기존/제안 작업, 미검증·사용자 결정·재개 조건은 최종 응답이나 승인된 PR 본문에 보고한다.

별도 Markdown 검증 보고서는 만들지 않고 PR 중복 분석 방지에 필요한 최신 상태만 설정된 단일 JSON에 갱신한다.

분석·제안과 실제 생성·관계 연결·상태 변경·제품 테스트 결과를 구분하며 실행하지 않은 작업을 성공으로 보고하지 않는다.
