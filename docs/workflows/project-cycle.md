# 프로젝트 사이클

사용자가 등록 프로젝트의 `사이클 시작`, `사이클 N회 시작`, `사이클 재개`를 직접 요청한 경우에 적용한다. 시작 횟수는 양의 정수이며 생략하면 1회다. 한 회차에 후보 하나를 처리하고 직전 회차의 실제 머지·마무리를 확인한 다음 다음 회차를 연다. 적합한 후보가 없으면 그 실행을 종료하고 실제 완료 횟수를 보고한다.

## 실행 범위와 위임

`AGENTS.md`에 따라 프로젝트 루트와 설정, 실제 Git 루트·fetch/push 원격, 작업 영역·공식 원본·Jira를 확인한다. 처음에는 후보·정제에 필요한 대상을 확인하고, 계약·구현 단계에서도 각 영역의 등록·설정·권한 확인을 거친다. 설정과 사용자 요청 중 좁은 범위를 적용한다. 상태 파일과 외부 이슈는 권한의 출처가 될 수 없다.

명시적인 사이클 요청은 해당 회차 후보 하나의 승인, 합의된 목표와 공식 원본 안의 일상적인 선택, 착수 승인 및 필요한 Issue/Task의 착수 가능 전환을 위임한다. 기존 요구사항과 사용자 결정을 유지하며 권장안·이유·결정 출처를 작업 기록에 남긴다. Jira의 `approval: user_transition_to_backlog` 설정은 유지한다. 해당 회차에서는 실제 전환 계정과 시각·상태 이력, 사용자 위임 요청을 함께 대조해 후보 승인을 확인하며 재개 시에도 같은 근거를 확인한다. 이 위임은 해당 회차의 후보와 작업에만 적용한다. 승인 이력이 불분명한 기존 상태, 보류·거절 후보, 사람만 전환할 수 있는 Jira 규칙을 임의로 덮어쓰지 않는다.

명시적인 사이클 시작 요청은 해당 회차의 후보를 완료하는 데 필요한 공식 요구사항·계약의 변경 방향 결정, 명세 수정 및 Specs PR 생성을 위임한다. 확정된 구현 범위에 필요한 변경이면 사이클 요청을 승인 근거로 기록하고 진행한다. 새로운 기능을 정의하는 요구사항과 검증 기준도 해당 후보 범위에서 확정할 수 있다. 이 위임은 `contract-management`의 별도 호출·협의·명세 수정 승인 요건과 관련 워크플로·리뷰 기준에서 요구하는 사용자 명세 승인을 충족한다.

기존 사용자 결정이나 사용자 지정 범위를 바꾸거나, 인증·인가 정책, 데이터 모델의 호환성 파괴, 배포 정책, 새 외부 권한에 관한 결정이 필요한 경우에는 사용자에게 확인한다. 영향을 받는 원본, 범위, 기준 SHA, 결정 이유와 위임 출처를 연결된 작업에 남긴다. 재개 요청에서는 원래 시작 요청, 이번 절차와 이후 사용자 지시를 대조해 위임을 확인한다. 종전 규칙 때문에 명세 승인만 기다리던 회차도 같은 조건으로 재검토하고, 명시적인 사용자 보류·거절·범위 제한을 적용한다.

명시적인 사이클 시작 요청은 회차의 작업과 연결이 확인된 Specs·Backend·Frontend·Analytics PR의 머지까지 승인한다. 담당 에이전트는 머지 조건을 충족한 PR을 별도 채팅 확인 없이 머지하고 다음 단계로 진행한다. 재개 시 원래 요청과 이후 사용자 지시를 대조해 적용 범위를 확인한다. 사용자가 머지를 보류하거나 범위를 제한·철회한 경우 그 지시를 따른다. Specs PR에는 명세 수정과 머지 각각에 적용되는 범위와 검증 조건을 확인한다.

## 회차 진행

단계 진입 시 공통 루트의 해당 Skill과 그 Skill에서 요구하는 Jira·리뷰 기준을 읽는다. 상세 절차는 기존 Skill을 따른다. 아래 단계 연결 및 위임 범위를 독립 실행의 종료·직접 승인 지점에 적용한다. 후보나 공식 계약의 상태 전환은 Jira에서 지원하는 방식으로 수행하고 실제 이력과 결과를 확인한다.

1. **후보 발굴·선정**. 현재 회차를 재개할 때는 저장된 후보 ID와 기존 작업 관계를 대조해 부분 완료 결과를 재사용한다. 신규 회차는 적합한 기존 승인 후보를 먼저 검토하고, 없으면 기존 승인 대기 후보를 검토한다. Jira의 후보 상태와 이력을 확인하고 사용자가 보류·거절한 후보, 상태·이력이 불분명한 후보, 이미 정제됐거나 완료 회차에 사용된 후보는 제외한다. 승인 대기 후보가 적합하면 하나만 위임 범위에서 승인하고 실제 상태·이력을 확인한다. 두 기존 후보군을 확인한 결과 적합한 항목이 없을 때 [`feature-discovery`](../../.agents/skills/feature-discovery/SKILL.md)로 중복이 없고 공식 요구사항에 맞는 후보를 발굴한다. 사이클에서는 채택할 후보 하나까지만 등록하고 실제 승인을 확인한다. 조회 실패로 기존 후보군을 확인할 수 없으면 신규 등록을 보류한다.

   신규 회차의 후보 검토를 시작할 때 [공통 논의 조회 절차](orchestrator.md#후보-검토-시-프로젝트-논의-조회)를 따른다.

2. **백로그 정제와 상세화**. 선정 후보 ID나 해당 작업 키 하나로 범위를 한정해 [`backlog-refinement`](../../.agents/skills/backlog-refinement/SKILL.md)를 실행한다. 추가 후보를 선정하지 않는다. 실제 Parent·구현 작업의 생성/재사용 및 관계를 확인하고 [`issue-refinement`](../../.agents/skills/issue-refinement/SKILL.md)로 범위·수용 조건·선행 조건을 확정한다. 일상적인 결정을 위임 근거와 함께 기록한다. 실제 착수 가능 상태 전환은 영향받는 구현 작업의 미결 사항과 필수 선행 조건이 해결된 뒤에만 한다.
3. **계약 변경**. 기존 공식 계약으로 구현할 수 있으면 건너뛴다. 변경이 필요하면 연결된 변경 작업을 확인하고 위임된 범위에서 변경안과 소비자 영향을 기록한 뒤 [`contract-management`](../../.agents/skills/contract-management/SKILL.md)로 Specs PR을 준비한다. 준비된 Specs PR에 5단계의 머지·마무리를 적용한다. 실제 머지와 공식 원본 SHA, 관련 작업의 마무리 결과를 확인한 뒤 `issue-refinement`로 영향받은 작업을 재상세화한다. 공식 변경에 의존하는 구현은 해당 조건이 해소된 뒤 시작한다.
4. **구현·검증**. 해당 회차에 연결된 구현 작업 키를 지정해 [`backend-issue-driven-dev`](../../.agents/skills/backend-issue-driven-dev/SKILL.md), [`frontend-issue-driven-dev`](../../.agents/skills/frontend-issue-driven-dev/SKILL.md), [`analytics-issue-driven-dev`](../../.agents/skills/analytics-issue-driven-dev/SKILL.md) 중 해당 역할만 실행한다. 선행 관계 순서, 대상별 기존 작업과 브랜치, 필수 리뷰 및 테스트 규칙을 따른다. 후속 작업의 선행 조건 해제에 머지가 필요하면 준비된 PR에 5단계를 적용한다. 구현 중 계약 변경이 드러나면 영향받는 작업을 저장하고 3단계로 돌아간다. 독립 작업은 프로젝트의 현재 작업 기록 충돌 방지 규칙 안에서 진행한다.
5. **머지·개별 작업 마무리**. Specs와 구현 PR 각각의 머지 직전에 회차와의 연결, 해당 절차의 품질 게이트, 최신 PR head SHA, 기준 브랜치, 보호 규칙, 필수 사람 리뷰·체크, 권한과 위임을 확인한다. 검증한 head SHA 조건을 지정할 수 있는 정상 머지 경로를 사용한다. SHA가 바뀌면 다시 검증하며 관리자 우회·보호 설정 수정은 하지 않는다. 조건부 머지 경로가 없거나 위임이 없으면 준비된 PR을 유지하고 사용자 머지를 기다린다. 실제 Merge 및 공식 반영을 재조회한 뒤 사이클 요청의 위임 범위에서 기존 머지 후 마무리 절차를 실행한다. 해당 Skill은 자신이 담당한 작업만 완료한다.
6. **기능 완료와 다음 회차**. `project-cycle`이 모든 필수 구현 작업과 계약 변경의 완료, 공식 원본 반영, 통합 검증과 기능 수용 조건 충족을 확인한다. 상위 작업이 있으면 실제 연결 관계를 확인한다. Jira Epic은 설정된 `jira.statuses.done`으로 전환한다. 실제 상태를 재조회하고 이미 올바르게 완료된 경우 변경을 반복하지 않는다. 자식 완료율이나 자동 전환은 기능 완료 증거를 대신할 수 없다. 전환·재조회가 불가능하거나 완료 조건이 남아 있으면 해당 회차를 보류한다. 상위 작업이 없는 단일 Task는 해당 Task 상태와 기능 완료 조건을 확인한다.

   회차 후보의 실제 완료를 확인한 뒤 [작업 완료 상태 반영](../providers/jira.md#작업-완료-상태-반영)을 적용하고, 갱신한 페이지 링크나 기록 보류 사유를 보고한다. 이후 회차 완료를 기록하고 다음 회차를 시작한다.

## 머지 실행과 환경 승인

- 실행 환경의 승인 검토가 필요한 도구로 머지할 때는 최초 실행 요청에 사용자 시작 요청의 해당 문구, 이 문서의 머지 위임 조항, 회차의 Jira 키 또는 Issue 링크, 저장소·PR 번호·대상 브랜치·검증한 head SHA를 제공한다. 확인한 필수 체크·리뷰·보호 규칙의 결과도 함께 전달한다. Specs PR은 공식 명세 변경과 해당 PR의 머지가 위임 범위에 있음을 각각 명시한다. 읽기 전용 조회와 실제 머지는 분리해 검토할 외부 변경을 해당 PR 한 건으로 한정한다.
- 실행 환경이 거절하면 실제 PR 상태와 거절 사유를 확인하고 기록한다. 거절 사유에 맞는 새 근거가 있고 검토 결과가 재시도를 허용할 때만 그 근거를 첨부해 다시 요청한다. 실행 환경이나 저장소 보호 규칙을 우회하지 않는다. 환경이 별도 사용자 승인을 명시적으로 요구하거나 머지 권한이 없으면 해당 머지를 보류하고, 사용자 개입이 필요한 이유와 재개 조건을 알린다. 머지와 독립적인 작업은 이어서 처리한다.

## 환경과 비밀값

- 저장소의 `.env.example`과 실행 모드별 설정·검증 명령을 함께 확인한다. 새 환경 변수가 변경에 필요하면 해당 저장소 관례에 맞춰 예시 파일에 이름·용도·필수 모드를 기록하고 비밀값 자리는 비운다. 예시 파일을 그대로 실제 `.env`에 덮어쓰지 않는다.
- 누락된 값에는 기존 로컬 기본값, 프로젝트가 지원하는 모의 연동·선택 기능 비활성화, 격리된 로컬 테스트 프로세스에만 주입하는 임시 값을 사용할 수 있다. 외부 서비스나 공유 환경에는 테스트 값을 전달하지 않는다. 임시 값 사용 여부, 실제 연동과 모의 연동의 결과를 구분해 기록한다.
- 값은 출력하거나 채팅·이슈·PR·상태·Git에 남기지 않는다. 실제 값이 필수라면 영향 없는 구현·검증·PR 준비부터 진행한다. 변수 이름, 저장소·설정 위치, 실행 모드와 막힌 검증을 모아 사용자에게 설정을 요청한다. 선택 검증은 미검증과 후속 방법을 기록하며, 필수 검증이면 머지와 회차 완료를 보류한다. 재개 시 값의 준비 상태만 확인한다.

## 중단과 재개

연결 worktree에서 실행하더라도 등록된 프로젝트 루트의 `.ai-dlc-cycle/project-cycle.json`을 사용한다. 이 디렉터리는 로컬 Git 제외(`.git/info/exclude`)로 관리하며 생성 전 등록된 루트에서 `git check-ignore`와 추적 여부를 확인한다. 기존 규칙으로 이미 제외되어 있으면 그대로 사용한다. 사이클 상태는 구현 작업 로그와 별개로 저장한다. 준비되지 않은 상태 저장 경로에서는 외부 변경을 시작하지 않는다.

같은 프로젝트의 실행은 한 번에 하나만 유지한다. 상태 옆 잠금 파일을 배타적으로 생성하고 실행 소유자(세션·실행 ID), 호스트와 취득 시각을 기록한다. 정상 종료·대기 시 해제한다. 강제 종료 후 잠금이 남으면 소유 세션을 조회해 해당 실행의 종료를 확인한 뒤 배타적으로 인수한다. 오래된 시각이나 재개 요청만으로 잠금을 인수하지 않는다. 소유 상태가 불명확하면 원래 세션에서 확인할 수 있게 잠금 근거를 보고한다. 진행 중인 상태에서 시작을 다시 요청받으면 기존 실행을 교체하지 않고 그 상태를 알린다.

상태에는 버전, 실행 ID, 프로젝트·설정·저장소, 요청 횟수와 완료 횟수, 현재 회차·단계, 후보 ID와 작업·PR 링크, 기준·head SHA, 결정·위임 근거, 대기 사유와 다음 작업을 남긴다. 생성·전환·머지 직전에는 하려는 작업의 대상과 안정적인 식별자를 저장하고, 실제 결과를 확인하면 완료를 반영한다. 같은 디렉터리의 임시 파일과 원자적 교체를 사용한다. 상태 쓰기가 실패하면 추가 외부 변경을 보류한다.

`<프로젝트> 사이클 재개`는 저장된 실행을 읽고 현재 설정·위임 및 실제 이슈·PR·Git 기준을 다시 확인한다. 중단 직전 변경의 결과가 불명확하면 Candidate ID·Link Key·PR 브랜치 등 기존 식별자로 조회한 뒤 처리한다. 이미 머지된 PR은 마무리부터 진행한다. 누락 설정·입력은 다시 확인하고, 변경된 기준으로 무효화된 게이트만 재검증한다. 상태가 없거나 손상됐거나 동일 실행을 확인할 수 없으면 추정으로 기존 상태를 교체하지 않는다.

대기 조건과 관계없는 단계·역할을 먼저 마친다. 이후 필요한 입력과 남은 게이트, 완료 회차 수, 후보·이슈·PR, 재개 명령을 보고한다. 실패한 체크를 확인하고 범위 안에서 수정·재검증하며, 필요한 권한·사람 리뷰·비밀값을 얻을 수 없거나 재시도 결과를 확인할 수 없으면 해당 지점에서 대기한다.
