# 공통 개발 절차

[공통 규칙](../../AGENTS.md), [Jira 절차](../providers/jira.md), [공통 리뷰](../review/shared.md)와 선택 영역의 리뷰 기준을 사용한다. 명시적 사이클은 [사이클 위임](project-cycle.md)을 적용한다.

## 설계와 재개

- Jira에서 승인된 범위·제외·완료 조건·선행 작업과 사용자 결정 출처를 확인한다. 필요한 공식 명세는 루트 설정에 지정된 원격 기본 브랜치의 같은 SHA에서 읽고 URL·SHA를 기록한다.
- 작업 브랜치에서 프로젝트 루트 `docs/current-task.md`에 Jira 키·대상 영역·승인 근거·관련 명세 SHA·설계·완료 조건과 검증 계획을 둔다. Jira의 상세 본문은 링크한다. 작업을 바꿀 때는 실제 이전 종료 여부를 확인하고 해당 작업의 미완료 기록을 보존한다.
- 루트 `docs/current-work-log.md`에는 해당 Jira 키, 마지막 단계, 승인·게이트, 브랜치·PR 참조, 장애와 다음 작업만 기록한다. 중단 전과 주요 외부 변경 직후 갱신한다. 검토 대기 중에는 최신 PR head를 유지하고 실제 GitHub 상태를 재조회한다. 수정이 필요해 head가 바뀌면 관련 검증을 다시 확인한다.
- 재개 시 기록을 단서로 Jira 키·역할·상태, Git 브랜치·diff·head, 해당 PR의 최신 CI·리뷰·머지 상태를 대조한다. 부분 변경은 안정적인 식별자로 재조회한 뒤 이어간다. Jira 링크 기록 전에 중단됐다면 [기존 작업 재개](../providers/jira.md#기존-작업-재개)의 PR 식별 절차를 따른다. 확인이 불가능하거나 상태·작업이 충돌하면 보류한다. Jira의 검토 중 상태를 진행 중으로 되돌리지 않는다.
- 같은 프로젝트·작업 트리에 두 작업의 현재 문서를 동시에 쓰지 않는다. 관련 없는 변경과 사용 중인 worktree를 보존한다. 외부 기록 및 상태가 불명확하면 다른 작업을 겹쳐 시작하지 않는다.

## 공통 명세

일반 구현에서는 공식 명세와 운영 설정을 읽기 전용으로 다룬다. 계약 변경이 필요하면 현재 계약을 지킬 대안을 검토하고, 변경 근거·대안·영향·원본 SHA·필요한 결정을 `docs/current-work-log.md`에 남긴다. 해당 범위를 보류하고 별도 계약 관리 절차를 안내한다. 이 기록을 위해 Jira 본문이나 댓글을 수정하지 않는다. 승인 및 실제 공식 반영 이후 설계·검증을 다시 확인한다.

## 진행 순서

1. [Jira 선정·상태 절차](../providers/jira.md#개발-task-상세-절차)로 작업과 역할, 선행 조건을 검증한다. 신규 착수만 가능한 전환을 확인해 진행 중으로 옮기고 재조회한다.
2. 루트 설정의 기준 브랜치와 승인 범위를 확인한다. 원격 기본 브랜치의 최신 SHA를 확인하고 그 SHA에서 작업 브랜치를 만든다. 브랜치 이름은 `development.branch_prefix`로 시작하며 Jira 키를 포함한다. 기본 브랜치에는 직접 push하지 않는다. 설정과 다른 기준이나 관련 없는 로컬 변경이 있으면 보류한다.
3. 설계와 기록을 갱신하고 승인된 영역을 구현한다. 환경별 검증 명령은 `areas.<역할>.development`에서 확인하고 해당 영역 디렉터리에서 실행한다. 여러 영역의 변경을 승인받았다면 각 영역의 리뷰·검증 기준을 적용한다. 새 Frontend 앱 소스는 JSX가 있으면 `.tsx`, 없으면 `.ts`를 사용하고 설정된 타입 검사와 관련 테스트를 실행한다.
4. 검토 가능한 diff와 근거가 준비되면 커밋·push하고 설정된 기본 브랜치로 PR을 연다. Jira에 그 PR 링크를 기록·재조회한 뒤 검토 중으로 전환한다. Jira의 일반 개발 중 변경 범위는 상태와 PR 링크다.
5. 사용자가 마무리를 요청하거나 사이클에서 위임한 마무리 단계라면 해당 PR의 실제 머지, 대상 브랜치와 완료 조건을 확인한다. Jira의 해당 작업만 완료로 전환·재조회하고 [Confluence 후보 완료 상태 반영](../providers/jira.md#작업-완료-상태-반영)을 수행한다. 안전한 경우 로컬 기준 브랜치를 fast-forward로 반영하고, 작업 브랜치는 미반영 내용과 다른 worktree의 사용이 없음을 확인한 경우에만 정리한다. 원격 브랜치 수동 삭제는 별도 요청 범위에서 수행한다.

## 독립 리뷰가 필요한 경우

Main은 자체 리뷰를 수행한다. 실제 diff가 인증·인가 동작, 데이터 마이그레이션 또는 여러 모듈의 동작에 영향을 주거나 사용자가 독립 리뷰를 요청하면 구현에 참여하지 않은 Architect에게 읽기 전용 검토를 맡긴다. 공통 루트·프로젝트 루트·설정 파일 절대 경로, 허용 영역·범위·금지 작업, 기준·검토 SHA, Jira 작업과 검사 결과를 전달한다. 필수 리뷰가 미완료이면 해당 품질 게이트를 보류한다. 팀이 요구하는 사람 리뷰는 별도로 확인한다.

## 품질 게이트

- **설계**는 범위·완료 조건·공식 계약·실행할 검증이 명확하고 필요한 사용자 결정이 확인되어야 한다.
- **구현과 리뷰**는 `docs/current-task.md`에 기록된 승인 범위와 diff를 대조하고 필요한 테스트와 설정된 명령을 실행한다. 확인된 실패·결함·필수 지적을 수정하고 관련 검증을 반복한다.
- **PR 준비**는 실행 가능한 검증과 적용되는 리뷰를 마친 상태다. 환경 때문에 남은 검증은 PR에 항목, 이유, 영향, 후속 방법, 머지 전 필수 여부를 적는다. 공식 원본·승인 누락이나 확인된 실패는 이 예외로 넘기지 않는다.
- **머지 준비**는 실제 최신 head의 필요 CI, 필수 리뷰·보호 조건, 충돌과 미해결 필수 지적을 확인한다. 대기·미실행·확인 불가는 통과로 보고하지 않는다. 독립 실행에서는 사용자가 머지한다.

### 개발 중 발견한 개선점 기록

현재 작업의 완료 조건에 필요한 문제는 해당 작업에서 해결한다. 독립적인 개선 가치가 있고 기존 작업이나 논의와 중복되지 않는 항목만 [프로젝트 논의 기록 Skill](../../.agents/skills/discussion-log/SKILL.md)을 통해 관찰 내용·영향·개선 방향과 Jira 또는 PR 링크를 남긴다. AI 제안과 확정 결정을 구분한다. 기록 실패는 보류 사유와 함께 보고하고 개발 마무리를 이어간다. 새 기능 후보 등록은 별도 후보 발굴 요청을 따른다.
