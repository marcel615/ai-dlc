# 통합 조정 절차

## 실행 경계와 설정 해석

후보 발굴·정제·기존 작업 상세화의 설정 파일은 루트 `AGENTS.md`의 선택 규칙을 따른다. 등록된 Specs가 없고 구현 대상이 하나뿐이면 해당 대상의 설정을 사용한다. Backend·Frontend·Analytics 중 요청에 필요한 활성 영역을 확인한다. 공식 원본이 필요한 범위는 선택된 설정에서 해당 원본을 확인한다.


먼저 공통 운영 루트의 `AGENTS.md`에 따라 프로젝트를 식별하고 대상 루트의 `ai-dlc.yaml`을 확인한다. 아이디어 제안 요청은 최대 3개 후보 등록, 백로그 정제 요청은 승인 후보 최대 2개의 정제와 필요한 작업 연결을 포함한다. 구체적인 등록·관계 처리는 선택 provider의 절차를 따른다. 정상 범위의 실행 승인을 반복 요청하지 않는다. 변경 영향 검토 요청은 분석·후속 작업 제안과 로컬 상태 갱신을 수행하며 실제 후속 작업 등록을 자동 실행하지 않는다. 사용자의 분석 전용·등록 제외·대상 제한 지시를 우선한다.

통합 저장소 자체의 문서·브랜치·커밋·Push·PR 유지보수는 사용자에게 요청받은 범위에서 수행한다. 후보 승인·중요한 정책·요구사항·계약·인증·DB 결정은 사용자에게 확인하고 미결정 범위를 임의 확정하지 않는다. `ai-dlc.yaml`의 `orchestrator.default_branch`에 직접 Push하지 않으며 자동 Merge는 하지 않는다. 서비스 제품 구현은 이 저장소의 Backend·Frontend·Analytics 개발 Skill에서 수행한다. Analytics 역할의 개발 절차는 `analytics-issue-driven-dev`에서 다룬다.

schema version 2에서 사용자 지정 서비스 키를 우선하고 없으면 `active_service`를 사용한다. 선택한 서비스의 `work_tracking.provider`가 없으면 `github_projects`다. `github_projects`는 기존 `project`, `labels`, GitHub Issue·관계 절차를 사용하고, `jira`는 독립된 `jira` 설정과 [Jira 작업 절차](../providers/jira.md)를 사용한다. 지원하지 않는 provider·버전, 필수 설정 누락·오류, 연결이나 권한 실패는 중단하고 보고하며 다른 도구로 대체하지 않는다. `repositories`, `requirements`, `contracts`는 두 경로에서 공통으로 해석한다.

`github_projects`에서 설정에 `backlog.parent_repository_role`과 `backlog.implementation_repository_roles`가 있으면 각각 Parent 저장소와 구현 대상을 지정한다. Specs 등록 없이 구현 대상이 하나뿐이고 해당 설정에 이 항목들이 없으면 기존 단일 저장소 Draft 흐름을 사용한다. 승인된 Draft를 선택한 구현 저장소의 Issue로 직접 전환하며 공통 Parent나 Sub-issue를 강제하지 않는다. 등록·설정·후보 범위가 일치하지 않거나 다른 역할의 작업이 필요한지 불명확하면 추측하지 않고 보류한다. Jira는 설정된 구현 저장소 역할과 `jira.role_labels`를 사용한다. 비활성 역할이 실제로 필요하면 그 부분의 계획·생성을 보류한다. 필요하지 않은 역할에 작업을 만들지 않으며, 비활성 상태 자체를 기능 대상외의 근거로 삼지 않는다.

단일 구현 저장소 설정에 `backlog` 항목이 없으면 루트 역할 선택 규칙의 `feature-discovery`와 `backlog-refinement`를 사용한다. 이 경우 후보 추적에 필요한 Project 또는 Jira 설정은 선택한 대상의 설정에서 확인한다. 값이 있지만 선택된 Skill이나 대상과 충돌한다면 임의로 덮어쓰지 않고 중단해 보고한다.

| 정보 | 원본 |
|---|---|
| 비전·후보·사용자 승인 | 선택한 provider의 후보와 확인된 사용자 승인 출처 |
| 공식 공통 요구사항 | `requirements`의 저장소 역할·경로·기본 브랜치와 조회한 SHA |
| 기능별 목적·범위·완료 조건·결정 이력 | 공식 요구사항을 참조하는 선택 provider의 후보 또는 기능 작업 |
| 구현·개발 상태 | 선택 provider의 구현 작업과 관련 GitHub PR·CI |
| API·인증·ERD·UI·분석 명세 | `contracts`의 계약별 저장소 역할·경로·기본 브랜치와 조회한 SHA |
| 표시 상태 | 선택 provider의 상태. 원본과 모순되면 확인 필요 |
| 중요한 결정 | 사용자 대화·코멘트의 작성자와 출처 |

`contracts.ui`는 화면 구성·라우팅·사용자 동작·로딩/빈 결과/오류·입력 검증/중복 제출 등 공통 UI 처리의 공식 기준이다. API·인증·데이터 구조는 각 공식 명세를 따르고, UI 내부 구현 설계·개발 진행 상태는 Frontend Issue·PR에서 확인한다. 기존 구현 저장소의 UI 문서나 코드로 공식 UI 명세를 대체하지 않는다. 공식 명세 간 충돌·미결정 사항은 Parent에 근거와 결정 질문을 남기며 임의로 확정하지 않는다.

`contracts.analytics`는 Specs 저장소에 둔 공식 분석 명세를 참조한다. 아이디어 발굴·백로그 정제·이슈 상세화에서 공식 분석 명세가 적용되는 작업은 입력 범위, 계산 규칙, 산출물과 지표 의미, 수용 기준을 설정된 원본과 대조한다. 구현 작업에 필요한 실행 환경과 재현 명령은 Analytics 저장소에서 확인한다.

백로그 정제에서는 후보의 사용자 흐름·수용 조건을 현재 공식 요구사항과 관련 계약의 원본에 대조한다. 이슈 상세화에서는 협의로 확정된 동작과 범위를 같은 기준으로 다시 대조한다. 변경 여부와 근거를 기능 작업에 기록한다. 새로 확정한 화면 동작이나 기존 기준과 다른 요구가 있으면 변경할 원본과 구현이 기다려야 할 범위를 식별한다. 이미 제공되는 기능의 명세 표기 정정은 구현의 선행 조건인지 별도로 판단한다. 원본을 확인하지 못했거나 결정이 남아 있으면 판정을 보류하고 이유를 기록한다.

필요성이 확인된 변경은 선택 provider의 절차에 따라 기존 Specs 작업을 재사용하거나 생성한다. Jira에서는 같은 기능과 공식 원본 저장소에 속한 변경을 하나의 Specs Task에 모으고, 상세화에서 확인한 변경은 재사용할 수 있는 기존 Task에 추가한다. 변경 항목별 대상·근거·기준 SHA와 영향을 받는 구현 작업, 실제 선행 여부 및 해제 조건을 기록한다. 작업 등록과 연결은 정제·상세화 범위에서 처리한다. 공식 원본 편집은 별도 `contract-management` 요청에서 사용자가 명세 수정을 승인한 뒤 수행한다. 같은 작업에서 검증을 거쳐 별도 승인 없이 명세 PR을 연다.

Jira 백로그 정제에서 선택 서비스의 `confluence.enabled: true`이면 기능 기획 페이지의 필요성을 판단하고 [Jira 작업 절차](../providers/jira.md)의 설정·중복·양방향 웹 링크·부분 실패 절차를 따른다. 설정 생략 또는 `enabled: false`는 Confluence 미사용이며 Jira 정제를 막지 않는다. 활성 설정이 누락되거나 유효하지 않거나 접근이 실패하면 Confluence 부분만 보류하고 Jira 결과와 초안을 보고한다. Jira 상태·완료 조건, Confluence 기능 기획·논의, 설정된 저장소의 공식 요구사항·계약을 구분한다.

Jira 이슈 상세화에서 Confluence가 활성화되면 [Jira 작업 절차](../providers/jira.md)에 따라 기존 기능 기획 페이지를 확인해 재사용하고, 없으면 필요성이 명확한 기능에 한해 설정된 위치에 생성·연결한다. 백로그 정제 선행 여부는 요구하지 않는다. 논의의 제안·판단·이유와 미결 사항은 기존 기획 내용 아래에 구분선으로 분리해 기록하고 기존 이력과 사용자 변경을 보존한다. 대상·중복·권한이 불명확하면 임의 생성·선택하지 않으며, Confluence 기록 실패는 Jira 결과와 구분해 보고한다.

계약 변경 협의는 결정 항목을 적절히 나누어 근거·대안·권장안을 제시하고 사용자의 판단을 기다린다. 방향과 영향이 명확해지면 명세 PR 전에 관련 구현 작업을 확인해 재사용하거나 필요한 누락 작업을 생성·연결하고 제안 상태와 선행 조건을 기록한다. 확인한 결정은 협의 중에도 기록하고, Jira에서는 댓글을 작성하지 않으며 [Jira 작업 절차](../providers/jira.md)에 따라 관련 본문과 연결된 Confluence 페이지에 반영한다. Confluence의 협의 기록은 기존 검토 아래에 구분선으로 분리한다. 개별 선택과 전체 명세 변경 승인은 구분하며, 이미 확인된 결정은 반복 확인하지 않는다.

`requirements`와 `contracts`의 `repository_role`을 선택 서비스의 `repositories`에 연결하고, 해당 역할의 `default_branch`에서 `path`를 조회한다. 실행 시 브랜치의 commit SHA를 먼저 확인하고 그 SHA로 문서를 읽어 원본 URL·commit SHA·경로를 기록한다. 같은 저장소의 원본은 같은 조회 기준 SHA를 사용하고 다른 저장소에는 각자의 SHA를 사용한다. `reference_commit`은 원본 저장소에서 확인한 조사 출발점이며 현재 버전을 고정하지 않는다.

공식 요구사항과 계약의 기준은 설정된 원본이다. 구현 저장소에 남아 있는 명세 사본은 구현 비교·과거 이력에만 사용하며 공식 원본으로 취급하지 않는다. 원본 조회 실패 시 구현 저장소의 사본이나 Parent 본문으로 대체하지 않고 필요한 작업을 보류한다. 원본·Parent·구현 간 불일치는 근거와 사용자 결정 필요 사항을 보고하며 어느 쪽도 임의로 덮어쓰지 않는다.

`templates/orchestrator/docs/`의 명세 문서는 초기 작성 양식이다. 대상 프로젝트의 명세로 작성·검토·승인하기 전에는 공식 원본으로 간주하지 않으며, 기존 공식 명세 파일을 덮어쓰지 않는다.

연결된 도구를 우선한다. 선택 provider의 필요한 기능이 부족하면 사용자 요청과 환경이 허용하는 기존 인증의 CLI/API를 사용한다. 기기별 실행 경로·인증 정보를 공통 정책에 고정하지 않는다. 목록은 마지막 페이지까지 확인하고 검색 결과만으로 부재를 확정하지 않는다.

연결 도구가 특정 작업에서 403 등 권한 오류를 반환하면 오류가 통합의 권한·설치 범위에 관한 것인지 확인한다. 사용자 요청 범위와 실행 환경이 허용하고 해당 작업 권한을 독립적으로 확인할 수 있다면 기존에 인증된 사용자 계정의 CLI/API를 대안으로 사용할 수 있다. 결과가 불명확하면 실제 상태를 먼저 재조회하고, 성공 후에도 변경 내용을 재조회한다. 사용자·저장소 정책의 명시적 거절이나 보호 규칙을 우회하지 않는다.

CLI 인증이 실패하면 곧바로 재인증을 요구하지 않는다. 연결 도구의 계정·기능을 확인하고, 실행 환경의 샌드박스가 OS 자격 증명 저장소에 접근하지 못할 가능성을 점검한다. 필요하면 실행 환경이 허용하는 승인 절차로 샌드박스 밖에서 기존 CLI 인증과 선택한 작업에 필요한 권한을 조회해 재시도한다. 예를 들어 Windows의 `gh`가 OS 자격 증명 저장소를 사용하는 경우 샌드박스 안팎의 인증 결과가 다를 수 있다. 토큰을 출력·복사·기록하지 않으며, 기존 인증과 필요한 권한을 확인할 수 없을 때만 부족한 접근과 재개 방법을 사용자에게 보고한다. 인증 성공과 작업별 쓰기 권한 확인은 별개다.

`github_projects` 작업을 쓰기 전에는 대상 저장소의 Issues 활성화·Issue와 라벨 변경 권한, Project 편집 권한·필드·선택지를 각각 확인한다. 공식 Sub-issue 관계가 필요한 작업에서는 그 추가·조회 지원과 소유자 조건도 확인한다. 저장소 접근 성공이나 Project 조회 성공은 외부 쓰기 성공의 증거가 아니다. 부족한 권한이나 관계 지원을 URL 링크로 우회하지 않는다. `jira`에서는 GitHub Project 편집·Draft·공식 Sub-issue 권한을 요구하지 않고 `docs/providers/jira.md`의 해당 Jira 작업별 권한·관계를 확인한다. GitHub의 코드·PR이나 공식 원본 조회에 필요한 접근은 선택 도구와 별도로 확인한다.

## 프로젝트 논의 기록

`discussion-log`는 사용자가 현재 대화의 프로젝트 논의를 기록해 달라고 요청할 때 독립 실행한다. `AGENTS.md`에 따라 선택한 설정의 schema version 2 서비스에서 `confluence`를 해석한다. 이 작업에는 Confluence 설정과 기록 대상 대화가 필요하며 `work_tracking.provider`와 관계없이 [프로젝트 논의 기록 절차](../providers/jira.md#프로젝트-논의-기록)를 적용한다. 설정·대상·쓰기 권한을 확인할 수 없으면 간결한 초안과 보류 사유를 보고한다.

## GitHub Projects 후보 제안·정제

이 절과 다음 `식별자·공식 관계·부분 실패` 절은 `github_projects` 전용이다. Jira의 후보 선정, 관계 및 재개 절차는 `docs/providers/jira.md`를 따른다.

제안은 `backlog.draft_skill`의 `feature-discovery`, 승인 후보 정제는 `backlog.refinement_skill`의 `backlog-refinement`가 담당한다. `issue-refinement`는 정식 Issue 상세 협의, `contract-management`는 사용자 직접 요청에 따른 계약 변경과 명세 PR, `change-impact-review`는 PR·계약 변경 영향을 분석한다. 각 Skill은 사용자 지시로 독립 실행하고 필요한 실제 원본을 직접 조회한다. 선행 Skill 실행을 요구하거나 다음 Skill·개발 사이클을 자동 시작하지 않는다. 기능 후보 발굴과 정제는 Orchestrator가 담당한다. 개발 중 발견한 필수 기술 후속 작업은 해당 저장소의 기존 절차와 중복 검사로 조정한다.

### 제안

`feature-discovery`는 사용자가 요청한 기능 아이디어를 요청 범위의 사용자 흐름과 Project 비전·필요한 공식 요구사항·계약·활성 구현 저장소·열린/닫힌 Issue·PR·기존 Draft와 비교한다. 유효 후보만 최대 3개 선정하며 필요성·차이·예상 효과·미결정 사항을 정리한다. 수를 채우기 위해 후보를 만들지 않는다. 필수 자료가 없으면 중복 확인 범위와 보류 사항을 명시하고 확인 전 등록하지 않는다.

`아이디어 제안해`는 설정된 Project에 유효 후보 최대 3개를 Pending Draft로 등록한다. 대상·권한·중복을 확인한 뒤 등록하며 후보마다 추가 승인을 요구하지 않는다. 사용자가 등록을 제외하면 본문·필드안만 보고한다. 이 요청은 후보 승인·백로그 정제·개발 시작 권한을 포함하지 않는다.

고유 Candidate ID와 식별 정보를 본문에 포함하고 설정된 AI 제안자·Pending 매핑을 사용한다. 개발 Status는 비운다. 비전·후보 승인은 사용자만 변경한다. 재개 시 이미 등록한 후보도 같은 요청의 최대 3개에 포함한다. 등록·필드 설정 결과가 불명확하면 식별자로 재조회하고 중복 여부 확인 전 재등록하지 않는다. 결과 보고 뒤 종료하며 승인·정제·개발을 자동 시작하지 않는다.

### 정제 후보 자동 선정

`백로그 정제해`에서 후보를 지정하지 않으면 설정된 Project의 Draft 전체를 페이지 끝까지 조회하고 실제 Approved 매핑인 후보를 자동 탐색한다. 사용자가 지정하면 지정 순서를 우선하되 승인·중복·목표·의존성 확인은 생략하지 않는다. 명시적으로 특정 후보만 요청했다면 범위 밖을 추가하지 않는다. 한 요청은 지정·자동 후보와 부분 성공 재개를 합쳐 최대 2개이며, 유효 후보가 부족하면 수를 채우지 않는다.

- 이미 정식 Issue로 전환되었거나 같은 기능이 존재하면 새 Parent를 만들지 않고 기존 작업·이력을 보고한다. 진행 중 부분 작업의 재개는 신규 후보 선정과 구분한다.
- 목표 자체가 불명확한 후보, 승인 확인 실패·우선순위 충돌·의존성 판단 불가·순환은 자동 선정에서 보류하고 이유를 보고한다. 상세 결정만 미정이면 질문·결정 라벨·Backlog로 정제할 수 있지만 착수 준비 완료로 취급하지 않는다.
- 후보의 우선순위는 Draft의 Project Priority를 설정 매핑으로 해석한다. 실제 Issue가 연결된 경우 라벨과의 충돌을 확인한다. 순서는 high→medium→low→미설정, 동률은 생성 시각이 오래된 순→안정적인 후보 ID 순이다. 필요한 값이 없거나 해석할 수 없으면 임의 추정하지 않는다.
- 실제 Issue의 Blocked by와 명시된 선행 조건을 확인한다. 후보 간 선행 관계가 확인되면 그 선행 후보를 먼저 정제한다. 선행 구현이 미완료여도 범위가 명확하면 정제는 가능하나 Backlog와 의존 관계를 유지한다. 정제를 개발 착수와 혼동하지 않는다.
- 지정 후보를 먼저 검토하고 남는 자리는 위 기준으로 선정한다. 지정 후보가 미승인·보류라면 그 사실을 보고한다. 선정·제외·보류·기존 작업 재사용의 근거와 조회 범위를 남긴다.

### 정제

Specs 없이 구현 대상 하나의 설정을 사용하는 단일 저장소 Draft는 위 승인·중복·우선순위·선행 관계를 확인하고 그 저장소의 Issue로 직접 전환한다. 후보 ID·승인 이력·Project 연결을 보존하고 본문·라벨·필드·상태를 재조회한다. 목표가 불명확하면 전환하지 않고 세부 결정만 남으면 결정 라벨과 Backlog를 사용한다. 이미 전환된 항목은 재사용하며 결과 불명 시 재조회 전 재생성하지 않는다. 다른 구현 역할이나 공통 추적이 필요한지 불명확하면 보류한다. 이 경우 아래 공통 Parent/Sub-issue 생성 단계는 적용하지 않는다.

1. `backlog-refinement`는 위 절차로 최대 2개를 선정하고 승인 출처·현재 Approved 매핑·전환 이력을 확인한다. 사용자나 다른 경로로 등록된 후보도 실제 승인을 확인해 처리할 수 있으며 `feature-discovery` 실행을 요구하지 않는다. 신규 아이디어 발굴·Draft 등록·승인 변경은 수행하지 않는다. 승인되지 않은 후보는 정식 Issue화하지 않는다. 목표가 불명확하면 Draft로 유지하고, 세부 결정만 남으면 결정 질문·설정된 결정 라벨과 Backlog 상태를 제안한다.

2. 작업에 필요한 공식 요구사항·계약과 설정된 관련 저장소의 열린·닫힌 Issue·PR·후보를 확인한다. 기존 Parent·구현 작업을 재사용하고 필요한 구현 범위만 나눈다. Parent와 구현안은 관련 공식 원본의 URL·SHA를 참조하고 기능별 범위·완료 조건을 작성한다. 각 구현안은 해당 저장소 템플릿과 독립 실행 요건을 따른다. 원본의 세부 명세를 복제하거나 정제만으로 변경을 승인하지 않는다.

3. Parent·구현 본문, 대상 역할, 식별자, 공식 관계, 우선순위·실제 선행 관계·미결정 사항을 정리한다. 분석·계획만 요청한 경우 여기서 보고하고 종료한다. 그 외에는 아래 생성·연결까지 수행한다. 개발은 시작하지 않는다.

Draft를 정식 Parent로 전환할 때는 원문을 그대로 앞에 나열하지 않고 목적·범위·제외 사항·확인된 결정과 출처·미결 사항·완료 조건·관련 작업과 공식 원본을 읽기 쉽게 정리한다. 원래 의도, 후보 식별자, 승인·결정 이력과 진행 상황을 보존하며 예시를 확정된 계약으로 바꾸지 않는다. 보존이 필요한 원문이나 해석이 불분명한 내용은 참고 영역에 원문 그대로 남기고, 미결 사항을 임의로 결정하지 않는다. 기존 본문 변경 전 최신 내용을 확인하고 변경 후 결과를 재조회한다.

4. 변경 직전 후보 승인·중복을 재확인하고, 기존 Parent가 없으면 Draft를 설정된 Parent 저장소의 Issue로 전환하는 방식을 우선한다. 원래 Draft를 남긴 채 별도 Parent를 추가 생성하지 않는다. 기존에 정식화된 후보는 임의 이동·복제하지 않고 이력을 보존해 공통 Parent 필요성을 판단한다.

5. 필요한 구현 Issue만 생성하거나 기존 Issue를 재사용하고 공식 Sub-issue 관계를 등록한다. Backend·Frontend·Analytics 중 실제로 필요한 역할만 처리한다.

6. Parent와 Sub-issue의 Project 등록·필드·공식 관계 결과를 재조회한다. 후보 승인·Candidate ID·연결 이력을 보존한다. 부분 성공이면 성공한 대상과 재개 지점을 보고하고 무조건 재실행하지 않는다.

## 식별자·공식 관계·부분 실패

후보 식별자는 `Project ID + Candidate ID`이며 기존 ID를 보존한다. ID가 없는 기존 Draft는 node ID를 사용한다. Parent에는 원본 후보·Project·ID를 남긴다. 구현 작업의 안정 식별자는 `Link Key: <Parent URL>|<대상 owner/repo>|<작업 식별자>`다. 같은 작업 재개 중 식별자를 바꾸지 않는다. 키가 없는 기존 작업도 목적·범위가 같으면 재사용한다.

필수 연계 작업이 공통 기능에 속하면 기존 Parent 아래에 연결한다. 특정 PR의 독립 기술 후속 작업은 원본 PR URL을 식별 기준으로 사용할 수 있으며, 단순 후속 작업마다 공통 Parent를 강제로 만들지 않는다.

공식 관계의 식별 기준은 Parent와 Sub-issue의 실제 Issue ID다. API의 Issue ID·node ID·저장소 내 번호를 혼동하지 않는다. 생성과 관계 추가는 별도 작업으로 확인한다.

| 현재 상태 | 처리 |
|---|---|
| 같은 작업 Issue 존재 | 생성 생략, 기존 작업 재사용 |
| 같은 Parent 관계 존재 | 관계 추가 생략, Project 등 남은 단계만 확인 |
| Parent 미지정 | 승인된 범위에서 공식 관계 추가 후 재조회 |
| 다른 Parent에 연결됨 | 자동 교체하지 않고 충돌 보고·사용자 판단 대기 |
| Issue 생성 후 관계 추가 실패 | 기존 Issue를 식별해 연결 단계부터 재개 |
| 관계 추가 후 Project 반영 실패 | Issue·관계 재생성 없이 Project 단계부터 재개 |
| Draft 전환 결과·생성 결과 불명 | 후보 식별자·전환 결과·Issue를 재조회, 확인 전 재생성 금지 |
| 관계 조회 실패 | 미연결로 추정하지 않고 해당 작업 보류 |

공식 관계 등록 후 Parent의 Sub-issue 목록과 자식의 Parent를 조회해 양쪽 ID를 확인한다. 본문 URL·체크리스트·관련 링크는 보조 근거일 뿐 관계 완료가 아니다. 다른 Parent를 가진 기존 작업은 참고 링크로 남길 수 있지만 이번 Parent의 Sub-issue로 연결되었다고 보고하지 않는다. 해당 작업의 완료 증거는 별도로 평가한다.

통합 조정은 Main의 단일 실행으로 수행한다. 검색으로 동시 생성을 원자적으로 막을 수 없으므로 경쟁 실행 시 쓰기를 보류한다. 구현 역할의 독립 개발은 계속 가능하다.

## 계약과 변경 영향

### Issue 상세화와 계약 변경 Issue

이 절의 Issue 저장소·Project 등록·공식 Sub-issue에 관한 절차는 `github_projects` 전용이다. Jira의 상세화·계약 작업 관리는 `docs/providers/jira.md`를 적용한다. 명세 변경 승인·Specs PR·실제 Merge 구분은 두 provider에 공통이다.

`issue-refinement`는 지정된 정식 Issue와 필요한 공식 관계·원본의 차이·미결 사항을 분석하고 선택지·장단점·권장안을 제시해 사용자와 협의한다. 단일 저장소 Draft에서 직접 전환된 Issue는 Parent나 Sub-issue가 없다는 이유로 보류하지 않으며, 실제 관계가 있다면 확인하고 보존한다. 확정된 결정과 공식 원본 URL·SHA를 관련 Issue에 반영한다. 착수는 사용자의 명시적 승인과 필수 조건 확인을 필요로 한다. 재상세화는 사용자 요청에 따라 수행하고 미병합 명세 PR을 공식 원본으로 취급하지 않는다.

백로그 정제·이슈 상세화·계약 관리에서 계약 변경 Issue가 필요하면 영향을 받는 공식 원본의 `repository_role`을 실제 저장소에 대응시킨다. 대상 원본이 하나의 저장소에 모이면 그 명세 저장소를 사용한다. 여러 저장소에 걸치거나 범위·저장소가 불명확하면 단일 Issue 위치를 추정하지 말고 사용자에게 관리 대상과 분할 여부를 확인한다. 선택한 저장소의 템플릿·권한과 설정된 Project를 확인한다.

관련 명세 저장소·Project의 열린/닫힌 Issue와 PR을 페이지 끝까지 조회하고 제목뿐 아니라 목적·계약 범위·상태·관련 링크·현재 원본 반영 여부를 비교한다. 같은 미완료 변경은 기존 Issue를 재사용하고 완료된 변경은 현재 계약에 이미 반영되었는지 평가한다. 서로 다른 변경은 별도로 관리한다. 검색·권한 실패, 중복 여부나 쓰기 결과 불명이면 부재로 간주하지 않고 재조회 전 생성하지 않는다. 동시 생성이 의심되면 쓰기를 보류한다.

Issue에 변경 필요성·근거, 영향받는 원본 URL·기준 SHA, 관련 Parent·Sub-issue, 사용자 결정과 출처·미결 사항을 기록한다. 기존 내용을 보존하며 상호 참조를 확인한다. 계약 Issue의 참조는 공식 Sub-issue 관계가 아니다. 설정된 Project에 실제 Issue가 이미 있는지 확인한 후 없으면 등록하고 필드·상태는 확인된 매핑과 근거에 따라 설정·재조회한다. 기존 담당자의 개발 상태나 승인 필드를 임의로 덮어쓰지 않는다. 부분 실패는 Issue·관계·Project 실제 상태를 재조회하고 남은 단계만 재개한다.

정제·상세화에서 계약 변경 Issue를 등록해도 명세 변경은 승인되지 않는다. `contract-management`는 사용자가 직접 요청했을 때만 독립 실행한다. 승인된 명세 변경으로 공식 명세 PR을 열고 사용자가 Merge한다. 관련 Issue별 영향과 재상세화 필요 여부를 기록하되 상세화를 자동 실행하지 않는다. 최신 공식 계약은 실제 Merge 후 기본 브랜치에서 다시 확인한다.

### 요청 시 PR 탐색과 이력

특정 PR을 지정하면 그 PR을 우선 확인한다. `변경 영향 검토해`처럼 지정이 없으면 선택 서비스의 활성·연결 확인된 저장소 역할 전체에서 신규·갱신 PR을 탐색한다. 공통 관리 저장소도 포함하고 같은 저장소는 한 번만 조회한다. 비활성·미연결 저장소는 누락 범위를 보고한다. 별도 상시 감시·서버·주기 작업은 만들지 않는다.

검토 재사용에는 `review.state_file`의 단일 JSON 상태를 사용한다. 검증 보고서를 생성·검색하지 않는다. 같은 파일의 서비스별 저장소·PR 최신 상태만 갱신하며 매 실행 이력을 누적하지 않는다. 파일이 없으면 빈 상태로 시작하고, 손상되었거나 읽지 못하면 완료로 추정하거나 임의 덮어쓰지 않고 그 한계를 보고한다.

1. 요청 시작 UTC를 이번 조회 상한으로 고정한다. 저장소별 마지막으로 확인한 완료 기준 시점을 하한으로 사용하고 경계 시각은 포함해 조회한다. 이력이 없는 첫 조회는 사용자가 기준 시점을 지정하지 않는 한 전체 PR 이력을 대상으로 한다. 사용자 지정 범위가 더 좁으면 그 범위만 검토한 것으로 기록한다.

2. open뿐 아니라 closed·merged를 포함한 PR 목록의 생성·갱신 시점과 최신 head/base를 페이지별로 조회한다. 요청 상한 이후 갱신은 다음 조회 대상으로 남긴다. 같은 PR은 저장소·번호로 합치며 조회 중 변동·누락이 의심되면 구간을 재확인한다.

3. 같은 PR URL·base SHA·head SHA·PR 상태와 관련 공식 요구사항·계약 원본의 저장소·경로·SHA·소비자 기준 SHA·PR 본문·관련 코멘트와 사용자 결정 출처 버전이 모두 같고 이전 분석이 완료된 경우만 상세 분석을 재사용한다. updatedAt은 탐색 단서이며 단독 완료 키가 아니다. 원본의 위치·요구사항·계약·소비자·결정 맥락이 바뀌면 갱신 PR뿐 아니라 영향을 받는 기존 검토 대상도 재평가한다. 이전 분석이 비공식 명세 사본을 기준으로 했다면 설정된 공식 원본을 기준으로 재검토한다.

4. 이전 보류·실패 건은 최신 PR 목록에 다시 나타나지 않아도 재개 대상으로 확인한다. 실제 diff로 영향 없음·호환 영향·비호환 영향·보류를 분류하고 영향 없는 변경도 이유·분석 버전을 기록한다. 검토 맥락이 그대로인 완료 건은 재분석하지 않고 재사용 사실만 보고한다.

5. 상태 파일의 해당 서비스·저장소·PR 항목을 최신 값으로 교체하고 다른 항목은 보존한다. 목록·필수 분석이 끝난 저장소만 완료 기준 시점을 전진시키고 실패·보류 건은 재개 대상으로 유지한다. 상세 결과·근거·누락 범위는 최종 응답이나 승인된 PR 본문에 보고한다. 상태를 저장하지 못하면 중복 생략을 보장하지 말고 한계를 보고한다.

상태 파일은 `schema_version: 1`, `services` 객체를 가진다. `services[서비스 키]` 아래에 다음 최신 값만 둔다. 빈 초기 상태는 실제 스캔·분석 완료를 뜻하지 않는다.

| 위치 | 저장할 최소 상태 |
|---|---|
| `repositories[owner/repo].completed_through` | 전체 조회·필수 분석이 끝난 UTC 상한. 미완료이면 이전 값 유지 또는 null |
| `pull_requests[PR URL]` | base_sha, head_sha, pr_state, source_updated_at, context, analysis_status, verdict, reviewed_at |
| PR의 `context` | 관련 공식 요구사항·계약의 저장소·경로·SHA, 소비자 SHA, PR 본문·관련 코멘트·사용자 결정의 버전 참조 또는 해시. 원문·비밀값은 저장하지 않음 |
| PR의 `analysis_status` | complete 또는 deferred. 실패·필수 정보 부족은 deferred로 남겨 재조회 |

관련 UI 명세도 `context`의 계약 원본에 포함한다. UI 원본 추가·변경으로 영향 범위가 달라지거나 이전 분석에 관련 UI 기준이 빠져 있으면 해당 분석을 재검토한다.

단일 PR 검토는 해당 PR 항목만 갱신하고 저장소 전체 완료 시점을 전진시키지 않는다. 변경·보류 PR은 최신 상태로 재검토하며 같은 맥락의 complete만 재사용한다. 상태 쓰기는 파일 전체를 검증해 교체하고 실패하면 이전 파일을 보존한다. 보고서·날짜별 상태 사본·별도 DB·실행 서버는 추가하지 않는다. 저장소 완료 시점은 PR 탐색 범위이며 기능 통합·배포 완료가 아니다.

### 변경 분석

공식 요구사항은 `requirements`, 분석 명세를 포함한 계약은 `contracts`에서 해석하고 위 원본 조회 절차를 적용한다. 현재 원본 SHA와 대상 PR base/head는 별도로 확인한다. 명세 저장소 PR은 해당 문서의 base/head를 비교하고, 구현 저장소 PR은 실제 구현 diff를 현재 공식 원본과 대조한다. 구현 저장소에 남아 있는 명세 사본의 변경만으로 공식 계약이 변경된 것으로 판단하지 않는다. OpenAPI가 설정되어 있지 않으면 존재를 가정하거나 사본을 만들지 않는다.

Parent는 공식 요구사항·API·인증·ERD·UI의 관련 URL·SHA를 참조해 기능별 범위·완료 조건·결정 이력을 관리한다. 원본 관리 역할은 사용자 승인에 따라 명세를 반영하고, 각 개발 Skill은 구현 일치성과 소비자 영향을 확인한다. 통합 AI-DLC는 변경 제안·원본 버전·연계 작업·검증 증거를 조율한다. 중요한 요구사항·계약·인증·DB·비호환 전환·최종 Merge는 사용자 결정이다. 통합 조정 저장소의 설정 변경만으로 연결 저장소의 문서·개발 절차가 수정되는 것은 아니다. 연결 저장소에 정리되지 않은 참조가 남아 있으면 필요한 후속 작업안으로 보고한다.

구현 저장소뿐 아니라 공통 요구사항·API·인증·ERD·UI 변경 PR도 영향 분석 대상이다. 대상 PR base/head SHA와 전체 변경 파일에서 시작하고 요구사항·계약·ERD·UI·화면·라우팅·엔티티·마이그레이션·DTO·컨트롤러·인증·관련 테스트 diff를 확인한다. patch 누락·잘림은 원문으로 보완한다. 본문이나 파일 이름만으로 판정하지 않는다.

| 판정 | 처리 |
|---|---|
| 영향 없음 | 계약·관측 동작 유지 근거를 남기고 추가 작업 미생성 |
| 호환 영향 | 기존 사용 유지 여부와 소비자 대응 필요성을 확인 |
| 비호환 영향 | 사용자 결정·소비자 대응·호환 기간·배포 순서·복구 제약 제시 |
| 판정 보류 | 원본 불일치·소비자 미연결 등 부족한 근거와 재개 조건 제시 |

`change-impact-review`는 선행 후보·정제 기록 없이도 지정 PR과 계약의 실제 원본으로 실행할 수 있다. 서버 차이·소비자 사용·Issue 필요성을 별도로 판단한다. 새 API 추가와 기존 요청의 인증 조건 변경은 분리한다. 미연결 소비자는 영향 없음이 아니다. 필수 연계 작업은 Issue안, 선택 기능은 별도 기능 검토가 필요한 사항으로 보고하되 Draft 등록·후보 승인·정제를 수행하거나 다른 Skill을 자동 호출하지 않는다. Merge된 PR의 사후 검토는 Merge 전 게이트 실증이 아니며 수동 검토로 Merge 차단을 보장하지 않는다.

## 상태·완료·재개

### 계약 작업 상태와 머지 후 마무리

`contract-management`는 계약 작업에만 아래 상태 전환을 적용한다. Jira는 설정된 프로젝트의 `jira.issue_types.contract`와 `jira.statuses`, GitHub Projects는 등록된 계약 Issue의 Project 상태 필드와 `project.statuses`를 사용한다. 해당 단계의 상태 매핑, 현재 상태, 전환 가능 여부와 권한을 확인하고 각 전환 결과를 재조회한다. 설정이나 권한을 확인할 수 없으면 해당 전환을 보류한다.

1. **진행 중** (`in_progress`). 확인된 계약 작업의 협의·영향 분석을 실제 시작할 때 전환한다. 재개 시 기존 검토 중·완료 상태를 되돌리지 않는다.
2. **검토 중** (`in_review`). 공식 원본의 설정된 기준 브랜치로 검토 가능한 명세 PR을 열고 계약 작업에 PR URL을 기록·확인한 뒤 전환한다. GitHub Issue에는 PR 링크를 남기고, 머지만으로 완료 조건 확인 전에 Issue나 Project 상태가 자동 종료되지 않도록 종료 참조와 Project 자동화의 영향을 확인한다.
3. **완료** (`done`). 사용자가 해당 PR의 머지 완료를 알리거나 마무리를 요청하면 작업과 연결된 필수 PR을 재조회한다. 설정된 공식 저장소와 기준 브랜치에 실제 Merge됐음을 모두 확인하고, 기준 브랜치에서 변경된 공식 원본과 현재 SHA를 다시 확인한다. 계약 작업과 영향받는 작업에 공식 SHA·선행 조건 충족 여부·재상세화 필요성을 기록·확인한 뒤 계약 작업만 완료로 전환한다. 연결된 구현 Task와 상위 작업의 상태는 유지한다. PR이 닫히기만 했거나 대상·연결·실제 반영이 불명확하면 완료를 보류한다.

실제 Merge를 확인한 같은 요청에서 명세 저장소의 작업 트리와 로컬 커밋을 확인한다. 안전하게 설정된 기준 브랜치로 이동할 수 있고 로컬 기준 브랜치가 원격과 같거나 뒤처져 있으면, 확인된 원격의 최신 상태를 fast-forward로 반영한다. 정리는 해당 PR용으로 사용한 로컬 작업 브랜치에 한한다. 다른 worktree에서 사용 중이거나, squash·rebase를 포함한 실제 반영 방식과 PR head를 대조했을 때 미반영 로컬 커밋이 있거나 그 여부를 확인할 수 없으면 브랜치를 보존한다. 이미 삭제된 브랜치는 완료된 정리로 처리한다. 원격 브랜치 수동 삭제는 별도 요청 범위에서만 수행한다. 최신화나 정리를 보류하면 계약 작업 완료 여부와 함께 사유를 보고한다.

재개 시 작업 상태, PR, 공식 기준 기록과 브랜치를 재조회하고 남은 단계만 수행한다. 상태 변경과 로컬 Git 정리의 성공·실패를 각각 보고한다.

### 통합 작업 상태와 완료

아래 Project 상태 전환 절차는 `github_projects` 전용이다. Jira는 `docs/providers/jira.md`의 사용자 수동 착수 가능 전환을 따른다. 통합 완료 증거와 부분 실패 재확인 원칙은 두 provider에 공통이다.

Draft 개발 상태는 비우고 승인 값은 사용자만 변경한다. 정식 Issue의 상태는 설정된 매핑을 사용한다. 미결정·선행 조건이 남으면 Backlog다. 개발 착수 준비를 표시할 때는 필수 조건과 사용자의 명시적 착수 승인을 확인한 뒤 Ready로 판단한다. Parent를 Ready로 전환할 때 공식 Sub-issue 각각의 범위·완료 조건·계약·승인·실제 선행 조건과 현재 Project 상태를 확인하고, 착수 조건이 충족된 Backlog 자식도 Ready로 전환해 재조회한다. 조건이 미충족이거나 확인되지 않은 자식은 보류 사유를 기록한다. 이미 Ready이거나 진행·검토·완료 중인 자식은 덮어쓰지 않는다. 이 최초 준비 상태 반영 이후 자식의 개발 상태는 담당 개발 Skill이 관리한다. 부모는 조정 시작 후 In Progress, 필요한 구현이 갖춰지고 통합 검증 대기면 In Review, 완료 조건 충족 후 Done이다.

백로그 정제 요청의 생성 작업에서 통합 AI-DLC는 Parent·Sub-issue 최초 Project 등록과 확인된 초기 상태·라벨을 설정한다. 이후 자식의 개발 상태는 담당 개발 Skill이 관리하며 통합 AI-DLC가 덮어쓰지 않는다. Parent 상태는 통합 AI-DLC가 근거로 판단한다. 우선순위는 Issue 라벨과 Project 매핑을 대조하고, 기한은 사용자 지정만 사용한다. 실제 선행 조건에만 Blocked by를 사용한다.

Parent 완료는 필요한 구현·계약 반영·통합 검증 증거를 모두 확인한 상태다. Sub-issues progress 100%나 단순 close로 완료하지 않는다. 개별 PR이 공통 Parent를 자동 종료하지 않도록 종료 참조·Project 자동화의 영향을 확인한다. 영향 검토에서는 불일치를 보고하고 필요한 수정안을 제안하며 검토 요청만으로 상태를 변경하지 않는다.

배포 필요 여부와 검증 환경은 Parent 완료 조건에서 정한다. 필요한 배포·검증이 미확인이면 보류하고, 모든 작업에 운영 배포를 일률적으로 요구하지 않는다. 제품 테스트 구현·실행은 각 개발 Skill 또는 사용자가 맡고 기존 CI·E2E 증거를 재사용한다.

생성·연결 작업에서는 Parent 본문·체크포인트에 후보/Link Key, 승인 출처, 단계별 성공 여부, Issue·관계·Project 식별자, PR head·계약 SHA와 남은 작업을 남긴다. 일반 검증 결과는 최종 응답이나 승인된 PR 본문에 보고하고 Markdown 보고서를 별도로 만들지 않는다. PR 분석의 재사용 상태만 단일 JSON에 갱신한다. 재개 시 실제 상태를 재조회하고 head·계약 변경에 관련 판정·검증을 갱신한다. 단순 close·not planned·Merge·배포를 구분하며 별도 DB는 만들지 않는다.
