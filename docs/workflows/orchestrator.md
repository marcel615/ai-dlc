# 통합 조정 절차

## 실행 경계와 설정 해석

[공통 규칙](../../AGENTS.md)에 따라 모노레포와 루트 `ai-dlc.yaml`을 확인한다. Jira 설정·권한과 GitHub 원격·기본 브랜치를 각각 확인한다. 승인된 범위의 후보 등록은 최대 3개, 독립 자동 정제는 최대 2개다. 명시적인 [프로젝트 사이클](project-cycle.md)은 회차 단위 위임과 단계 연결을 적용한다. 영향 검토만으로 후속 작업을 등록하거나 상태를 변경하지 않는다.

Jira는 작업 범위·완료 조건·승인 출처·상태를, Confluence는 기획·논의·후보 상태 표시를, GitHub는 코드·PR·리뷰·CI를 관리한다. 공식 요구사항·계약은 루트 설정의 `requirements`와 `contracts`에 지정한 Specs 경로에서 읽는다. 원격 기본 브랜치 SHA를 확인하고 관련 파일을 모두 그 SHA에서 읽어 파일별 URL·경로와 공통 SHA를 기록한다. 사본·템플릿·미병합 PR은 공식 원본으로 사용하지 않는다. 조회 실패·충돌·결정 대기는 필요한 범위를 보류한다.

UI는 사용자 흐름, 라우팅, 상태 및 입력 처리까지 확인한다. Analytics는 입력 범위·계산 규칙·산출물·지표·수용 기준을 확인한다. 담당 영역이나 필요한 공식 원본이 없으면 그 범위만 보류한다. 연결 도구를 우선하고 권한이 확인된 CLI/API를 사용할 수 있다. 목록을 끝까지 확인하고 권한 오류나 조회 실패는 결과 부재로 판단하지 않는다.

## 후보 검토 시 프로젝트 논의 조회

독립 `feature-discovery`와 프로젝트 사이클의 신규 회차에서 후보 검토를 시작할 때 이 절차를 사용한다. 같은 회차에서 신규 발굴로 넘어가면 앞서 확인한 논의 자료를 재사용할 수 있다.

1. 프로젝트의 Confluence가 활성화되어 있으면 [프로젝트 논의 기록 설정](../providers/jira.md#프로젝트-논의-기록)에 따라 상위 페이지를 확인하고, 직계 하위의 `작업 후보와 진행 상태` 페이지를 조회한다. 후보의 `논의` 링크와 관련 날짜별 기록에서 기획 배경, 사용자 판단, 미결 사항을 확인한다. 날짜별 기록에 남아 있는 후보도 확인한다.
2. `검토 중` 항목은 신규 발굴이 필요할 때 검토한다. 작업 키가 있는 관련 항목은 연결된 Jira 또는 GitHub 작업의 현재 상태와 등록 이력을 확인해 중복 등록을 피한다. 후보는 공식 원본과 기존 작업에 대조하고, 등록된 후보의 적격 여부와 승인은 선택한 작업 추적 도구의 상태와 이력으로 판단한다.
3. Confluence는 조회만 한다. 설정이 없거나 비활성화되어 있거나 관련 페이지를 확인할 수 없으면 조회 범위를 보고하고, 확인 가능한 날짜별 기록과 다른 자료로 검토를 이어간다.

## 프로젝트 논의 기록

`discussion-log`는 사용자가 현재 대화의 프로젝트 논의를 기록해 달라고 요청할 때 독립 실행한다. `AGENTS.md`에 따라 프로젝트 루트 설정의 `confluence`를 확인한다. 이 작업에는 Confluence 설정과 기록 대상 대화가 필요하며 [프로젝트 논의 기록 절차](../providers/jira.md#프로젝트-논의-기록)를 적용한다. 설정·대상·쓰기 권한을 확인할 수 없으면 간결한 초안과 보류 사유를 보고한다.

[공통 개발 마무리](development.md#개발-중-발견한-개선점-기록)에서 선별한 개선점을 기록할 때도 같은 Confluence 기록 절차를 사용한다.

## 식별자·공식 관계·부분 실패

후보는 Jira의 기존 Candidate ID와 작업 키로 식별한다. 신규 구현 Task는 `Link Key: <상위 Jira 작업 키>|<영역>|<작업 식별자>`로 식별한다. 이미 존재하는 작업은 이전 저장소형 Link Key, Jira 관계, 역할 라벨, 역할별 범위와 완료 조건을 함께 대조해 재사용한다. 기존 키와 관계를 보존한다. 생성·연결·상태 변경은 [Jira 절차](../providers/jira.md)를 따르고 쓰기 결과가 불명확하면 안정 식별자로 실제 상태를 먼저 재조회한다.

## 계약과 변경 영향

### Issue 상세화와 계약 변경 Issue

선택한 작업과 관련 계약·구현을 대조하고 확정 동작·근거·미결 질문·완료 조건·선행 관계를 Jira에 반영한다. Confluence 협의는 해당 기능 또는 계약 페이지의 기존 결정과 이력을 보존하며 [Jira 절차](../providers/jira.md)를 적용한다. 기능 전체 완료를 추적해야 할 때 Epic을 사용하고, 독립 단일 작업에는 추가 계층을 만들지 않는다.

공식 계약 변경 필요성이 확인되면 관련 기능 및 원본 경로와 영향 범위가 같은 기존 Specs Task를 우선 확인한다. 필요한 작업과 차단 관계를 실제 Jira에서 확인하고, Merge가 실제 선행 조건인 범위와 병행 가능한 범위를 구분한다. Specs Task 등록은 명세 수정 승인이 아니다. 별도 `contract-management` 요청과 승인 또는 유효한 사이클 위임으로 공식 명세 변경과 Specs PR을 진행한다. 명세 기준 갱신과 차단 해제는 설정 기준 브랜치에 실제 머지된 원본 SHA를 확인한 뒤 처리한다.

### 요청 시 PR 탐색과 이력

특정 PR은 설정된 모노레포의 실제 PR인지 확인한다. 지정이 없으면 저장소의 신규·갱신 PR을 한 번씩 탐색한다. 별도 상시 감시는 만들지 않는다.

검토 재사용에는 `review.state_file`의 단일 JSON 상태를 사용한다. 검증 보고서를 생성·검색하지 않는다. 같은 파일의 저장소·PR 최신 상태만 갱신하며 매 실행 이력을 누적하지 않는다. 파일이 없으면 빈 상태로 시작하고, 손상되었거나 읽지 못하면 완료로 추정하거나 임의 덮어쓰지 않고 그 한계를 보고한다.

1. 요청 시작 UTC를 이번 조회 상한으로 고정한다. 이 저장소의 마지막으로 확인한 완료 기준 시점을 하한으로 사용하고 경계 시각은 포함해 조회한다. 이력이 없는 첫 조회는 사용자가 기준 시점을 지정하지 않는 한 전체 PR 이력을 대상으로 한다. 사용자 지정 범위가 더 좁으면 그 범위만 검토한 것으로 기록한다.

2. open뿐 아니라 closed·merged를 포함한 PR 목록의 생성·갱신 시점과 최신 head/base를 페이지별로 조회한다. 요청 상한 이후 갱신은 다음 조회 대상으로 남긴다. 같은 PR은 저장소·번호로 합치며 조회 중 변동·누락이 의심되면 구간을 재확인한다.

3. 같은 PR URL·base SHA·head SHA·PR 상태와 관련 공식 요구사항·계약 원본의 저장소·경로·SHA·소비자 기준 SHA·PR 본문·관련 코멘트와 사용자 결정 출처 버전이 모두 같고 이전 분석이 완료된 경우만 상세 분석을 재사용한다. updatedAt은 탐색 단서이며 단독 완료 키가 아니다. 원본의 위치·요구사항·계약·소비자·결정 맥락이 바뀌면 갱신 PR뿐 아니라 영향을 받는 기존 검토 대상도 재평가한다. 이전 분석이 비공식 명세 사본을 기준으로 했다면 설정된 공식 원본을 기준으로 재검토한다.

4. 이전 보류·실패 건은 최신 PR 목록에 다시 나타나지 않아도 재개 대상으로 확인한다. 실제 diff로 영향 없음·호환 영향·비호환 영향·보류를 분류하고 영향 없는 변경도 이유·분석 버전을 기록한다. 검토 맥락이 그대로인 완료 건은 재분석하지 않고 재사용 사실만 보고한다.

5. 상태 파일의 해당 저장소·PR 항목을 최신 값으로 교체하고 다른 항목은 보존한다. 목록·필수 분석이 끝난 저장소만 완료 기준 시점을 전진시키고 실패·보류 건은 재개 대상으로 유지한다. 상세 결과·근거·누락 범위는 최종 응답이나 승인된 PR 본문에 보고한다. 상태를 저장하지 못하면 중복 생략을 보장하지 말고 한계를 보고한다.

상태 파일은 `schema_version: 1`, `services` 객체를 가진다. `services[서비스 키]` 아래에 다음 최신 값만 둔다. 기존 상태 형식을 유지하고 새 항목에는 설정된 owner/repo를 프로젝트 키로 사용한다. 역사적 항목과 이전 저장소 기준점은 보존하며 현재 저장소의 완료 기준으로 전용하지 않는다.

| 위치 | 저장할 최소 상태 |
|---|---|
| `repositories[owner/repo].completed_through` | 전체 조회·필수 분석이 끝난 UTC 상한. 미완료이면 이전 값 유지 또는 null |
| `pull_requests[PR URL]` | base_sha, head_sha, pr_state, source_updated_at, context, analysis_status, verdict, reviewed_at |
| PR의 `context` | 관련 공식 요구사항·계약의 저장소·경로·SHA, 소비자 SHA, PR 본문·관련 코멘트·사용자 결정의 버전 참조 또는 해시. 원문·비밀값은 저장하지 않음 |
| PR의 `analysis_status` | complete 또는 deferred. 실패·필수 정보 부족은 deferred로 남겨 재조회 |

관련 UI 명세도 `context`의 계약 원본에 포함한다. UI 원본 추가·변경으로 영향 범위가 달라지거나 이전 분석에 관련 UI 기준이 빠져 있으면 해당 분석을 재검토한다.

단일 PR 검토는 해당 PR 항목만 갱신하고 저장소 전체 완료 시점을 전진시키지 않는다. 변경·보류 PR은 최신 상태로 재검토하며 같은 맥락의 complete만 재사용한다. 상태 쓰기는 파일 전체를 검증해 교체하고 실패하면 이전 파일을 보존한다. 보고서·날짜별 상태 사본·별도 DB·실행 서버는 추가하지 않는다. 저장소 완료 시점은 PR 탐색 범위이며 기능 통합·배포 완료가 아니다.

### 변경 분석

공식 요구사항과 계약은 루트 설정의 경로로 식별한다. 최신 기본 브랜치 SHA와 대상 PR base/head는 별도로 확인한다. 설정된 명세 경로의 변경은 PR base/head에서 비교하고, 구현 diff는 관련 공식 원본과 대조한다. 같은 PR에 두 유형이 모두 있으면 각각의 영향과 조합을 확인한다. 영역은 승인된 역할 경로와 실제 전체 diff로 식별한다.

대상 PR base/head SHA와 전체 변경 파일에서 시작하고 요구사항·계약·ERD·UI·화면·라우팅·엔티티·마이그레이션·DTO·컨트롤러·인증·관련 테스트 diff를 확인한다. patch 누락·잘림은 원문으로 보완한다. 본문이나 파일 이름만으로 판정하지 않는다.

| 판정 | 처리 |
|---|---|
| 영향 없음 | 계약·관측 동작 유지 근거를 남기고 추가 작업 미생성 |
| 호환 영향 | 기존 사용 유지 여부와 소비자 대응 필요성을 확인 |
| 비호환 영향 | 사용자 결정·소비자 대응·호환 기간·배포 순서·복구 제약 제시 |
| 판정 보류 | 원본 불일치·소비자 미연결 등 부족한 근거와 재개 조건 제시 |

`change-impact-review`는 선행 후보·정제 기록 없이도 지정 PR과 계약의 실제 원본으로 실행할 수 있다. 서버 차이·소비자 사용·Issue 필요성을 별도로 판단한다. 새 API 추가와 기존 요청의 인증 조건 변경은 분리한다. 미확인 소비자는 영향 없음이 아니다. 필수 연계 작업은 Issue안, 선택 기능은 별도 기능 검토가 필요한 사항으로 보고하되 후보 등록·승인·정제를 수행하거나 다른 Skill을 자동 호출하지 않는다. Merge된 PR의 사후 검토는 Merge 전 게이트 실증이 아니며 수동 검토로 Merge 차단을 보장하지 않는다.

## 상태·완료·재개

### 계약 작업 상태와 머지 후 마무리

`contract-management`는 계약 작업에만 아래 상태 전환을 적용한다. `jira.issue_types.contract`와 `jira.statuses`를 사용한다. 해당 단계의 상태 매핑, 현재 상태, 전환 가능 여부와 권한을 확인하고 각 전환 결과를 재조회한다. 설정이나 권한을 확인할 수 없으면 해당 전환을 보류한다.

1. **진행 중** (`in_progress`). 확인된 계약 작업의 협의·영향 분석을 실제 시작할 때 전환한다. 재개 시 기존 검토 중·완료 상태를 되돌리지 않는다.
2. **검토 중** (`in_review`). 공식 원본의 설정된 기준 브랜치로 검토 가능한 명세 PR을 열고 계약 작업에 PR URL을 기록·확인한 뒤 전환한다.
3. **완료** (`done`). 사용자가 해당 PR의 머지 완료를 알리거나 마무리를 요청하면 작업과 연결된 필수 PR을 재조회한다. 설정된 공식 저장소와 기준 브랜치에 실제 Merge됐음을 모두 확인하고, 기준 브랜치에서 변경된 공식 원본과 현재 SHA를 다시 확인한다. 계약 작업과 영향받는 작업에 공식 SHA·선행 조건 충족 여부·재상세화 필요성을 기록·확인한 뒤 계약 작업만 완료로 전환한다. 연결된 구현 Task와 상위 작업의 상태는 유지한다. PR이 닫히기만 했거나 대상·연결·실제 반영이 불명확하면 완료를 보류한다.

실제 Merge를 확인한 같은 요청에서 모노레포 작업 트리와 로컬 커밋을 확인한다. 안전하게 설정된 기준 브랜치로 이동할 수 있고 로컬 기준 브랜치가 원격과 같거나 뒤처져 있으면, 확인된 원격의 최신 상태를 fast-forward로 반영한다. 정리는 해당 PR용으로 사용한 로컬 작업 브랜치에 한한다. 다른 worktree에서 사용 중이거나, squash·rebase를 포함한 실제 반영 방식과 PR head를 대조했을 때 미반영 로컬 커밋이 있거나 그 여부를 확인할 수 없으면 브랜치를 보존한다. 이미 삭제된 브랜치는 완료된 정리로 처리한다. 원격 브랜치 수동 삭제는 별도 요청 범위에서만 수행한다. 최신화나 정리를 보류하면 계약 작업 완료 여부와 함께 사유를 보고한다.

재개 시 작업 상태, PR, 공식 기준 기록과 브랜치를 재조회하고 남은 단계만 수행한다. 상태 변경과 로컬 Git 정리의 성공·실패를 각각 보고한다.

### 통합 작업 상태와 완료

Jira Epic 완료는 필요한 구현·계약 PR의 실제 머지, 요구된 환경의 통합 검증과 기능 수용 조건을 확인한 뒤 처리한다. 자식 완료율이나 PR 종료로 추정하지 않는다. 배포는 실제 기능 완료 조건에 따라 확인한다. 재개 시 후보·작업·PR 식별자, 승인 출처, 관련 SHA와 실제 상태를 확인해 이미 성공한 단계를 건너뛴다.
